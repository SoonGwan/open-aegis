# 작업 분류 계약

작업 분류는 조직을 위한 메타데이터다. 분류를 지정·해제해도 실행 상태, 승인,
범위 스냅샷, 검사 목록, 계획과 Worker 결과는 바뀌지 않는다. 운영자와 관리자가
분류를 만들고 수정·보관·복원하며 작업에 지정할 수 있다. 열람자는 읽기만 가능하다.
저장 직전 DB의 현재 역할과 비활성 여부를 다시 확인한다.

## 저장과 이력

활성 이름은 대소문자를 무시해 중복을 막는다. 이름은 80자, 분류는 보관된 항목을
포함해 1,000개까지다. 수정·보관·복원에는 검토한 분류 버전이 필요하다.
각 버전의 스냅샷과 수행자·감사를 같은 트랜잭션에 저장한다. 보관은 기존 작업의
분류를 지우지 않으며, 새 지정은 거절한다. 복원 시 활성 이름 중복을 다시 확인한다.

생성은 수행자와 요청 ID로 중복을 방지한다. 같은 입력 재시도는 기존 분류의 현재
버전을 돌려주며, 같은 요청 ID의 다른 입력은 409다. 수정 충돌 화면은 입력을
유지하고 현재 이름·버전을 보여 준다. 사용자가 최신 버전을 명시적으로 검토한 뒤
다시 저장한다. 오류가 나는 동안 입력을 자동 덮어쓰지 않는다.

## 여러 작업 변경

한 요청에서 1–25개 작업의 현재 분류 변경 버전을 함께 제출한다. 하나라도 없거나
버전이 달라졌거나 분류가 보관됐다면 전체 요청을 거절한다. 모든 작업의 분류,
이전/새 분류 이력, 변경 영수증과 감사를 원자적으로 저장한다.

같은 수행자·요청 ID·입력의 재시도는 처음 저장한 결과를 돌려준다. 이후 다른 사람이
분류를 바꿔도 그 영수증은 변하지 않는다. 작업 순서만 바뀐 재시도는 같은 요청이다.
저장 뒤 응답을 받지 못한 경우 화면은 입력과 요청 ID를 유지해 중복 없이 재시도한다.
모달을 닫은 뒤에는 미확인 요청을 복원하지 않는다.

화면의 선택은 선택 당시 버전을 고정한다. 주기적인 목록 갱신이 새 버전을 자동
채택하지 않는다. 충돌 시 창을 닫고 선택을 해제한 뒤 현재 작업을 다시 선택한다.
전체 작업 또는 특정 분류의 작업을 SQL에서 검색·집계·페이지 조회한다. 한 페이지는
25개다. 분류 목록의 검색·상태·페이지는 URL에 남지만 작업 선택/모달은 URL에 남지 않는다.

작업에는 지정 당시 분류 이름·분류 버전이 남는다. 분류 이름을 나중에 바꾸어도
과거 작업의 표시와 변경 이력을 다시 쓰지 않는다. 목록의 작업 보기는 안정적인 분류
ID를 사용하므로 이름 변경·보관 뒤에도 같은 작업을 찾는다.

재계획·재시도·결과/관찰 후속 계획은 원본 분류와 출처를 이어받으며 새 작업의 변경
버전은 0부터 시작한다. 새 작업을 명시적으로 재분류하면 이전 상속 출처를 이력에
보관하고 현재 상속 표시를 제거한다. 이후 파생 작업은 새 작업의 분류를 이어받는다.
템플릿의 문자열 분류 라벨과 작업 분류 ID는 별개다.

## API

- `GET/POST /api/task-categories`, `GET/PUT /api/task-categories/{id}`
- `POST /api/task-categories/{id}/archive`, `GET /api/task-categories/{id}/history`
- `POST /api/tasks/category-assignment`: `task_ids`, 필수 nullable `category_id`,
  정확히 같은 작업들의 `expected_revisions`, `request_id`
- `GET /api/tasks/{id}/category-history`
- `GET /api/records/tasks?category_id={id}`: 분류별 SQL 건수·페이지
- `category_id=unclassified`: 분류가 없는 작업만 조회

분류·작업 변경 이력은 25개 페이지이며 삽입 워터마크는 이후 삽입을 제외한다.
기존 행의 수정은 현재 상태로 읽는다. 분류 필터는 작업에만 허용한다.

전체 모바일·보조 기술, 모달/미확인 저장의 새 문서 복원, 템플릿 라벨과 분류 ID 통합,
구버전 쓰기와 분류 출처 보존의 교차 버전 검수는 별도 출시 기준으로 남는다.
