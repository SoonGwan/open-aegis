# 제공자 호출 시도 기록

새 계획/AI 대화 호출은 `records.kind=llm_calls`에 독립된 시도 ID로 기록된다.
시작 기록과 감사 이벤트가 저장된 다음에만 제공자 호출을 시도한다. 시작 저장이
실패하면 호출하지 않는다. 제공자 결과의 사용량/가격/형식 검증 결과는 답변/계획
저장 전에 별도 트랜잭션으로 관찰 기록과 감사 이벤트에 보존한다.

이 구조는 제공자 호출 후 세션 폐기나 계획/답변 저장 실패가 발생해도, 관찰된
사용량을 메시지와 함께 잃지 않기 위한 것이다. 실제 제공자가 요청을 수신했거나
청구했다는 증명은 아니다. DNS/TLS/전송 실패도 호출 시도에 포함하며 미확인
사용량은 0으로 계산하지 않는다.

## 상태와 연결

| state | 의미 |
|---|---|
| started | 시도를 저장했으나 결과 관찰 기록이 없음; 전송/청구 여부 미확인 |
| observed | 사용량/가격/검증 결과를 저장했으나 계획/답변 연결 미확정 |
| committed | 계획/답변과 시도 연결을 같은 저장 트랜잭션에서 확정 |
| uncommitted | 세션 폐기·저장 실패 등으로 결과를 계획/답변에 저장하지 못함 |
| interrupted | 독점 서버 시작 시 이전 started/observed 기록을 발견; 관찰된 값은 보존 |

`source`는 planner 또는 conversation이다. task_id, model, started_at, observed_at,
tokens, cost와 제공자 origin(경로·query·인증 정보 제외)을 보존한다.
대화는 시작 때 인증한 actor_id도 남기며 planner actor는 현재 null이다.
프롬프트·질문·제공자 답변/오류 본문·키·쿠키·전송 토큰은 시도에 저장하지 않는다.
비용 quote는 별도로 운영자가 제공한 가격 근거를 포함한다([비용 계약](LLM-COSTS.md)).
committed 시도에는 record_kind/record_id와 settled_at이 있어 실제 계획/답변을
조회할 수 있다. 해당 메시지/계획 메타데이터의 call_id로 시도를 역으로 찾는다.

응답 형식 outcome=accepted는 계획/답변의 저장 성공을 뜻하지 않는다. 형식상 수용
결과도 세션 폐기 뒤 uncommitted일 수 있다. 응답이 거절돼 규칙 요약을 저장했다면
invalid_answer + committed다. 이 두 축을 화면과 조회에서 구분한다.

성공한 전송 ID 재조회는 원래 답변과 call_id를 반환하고 새 호출을 하지 않는다.
이전에 답변을 저장하지 못한 전송 ID의 **수동 재시도는 새 제공자 호출/시도**가
될 수 있다. 원래 실패 시도를 덮어쓰지 않는다. 자동 제공자 재시도는 하지 않는다.

## 읽기 API와 집계

- `/api/llm/calls`: 인증된 모든 역할의 읽기 전용 SQL 페이지. 기본25/최대100,
  offset, 삽입 watermark snapshot, search(id/model/source/state/task_id),
  task_id/source/state 필터를 지원한다. 갱신된 상태는 실시간이며 watermark는 과거
  DB 상태의 복원이 아니다. 원문 프롬프트·답변을 반환하지 않는다.
- `/api/llm/usage?ledger=attempts&source=all`: 시도별 집계와 attempt_states, 보고 토큰,
  검증된 통화별 비용 부분 합계를 같은 SQLite 읽기 스냅샷에서 반환한다.
  기간은 **started_at** 기준이다. 미저장/중단 시도의 관찰 사용량도 포함한다.
- 기존 `/api/llm/usage` 기본값은 ledger=persisted/source=planner를 유지한다.
  이 모드는 마지막 계획/저장된 메시지를 observed_at 기준으로 집계한다.
  두 집계를 더하면 같은 성공 호출을 중복 계산하므로 하나의 기준을 선택한다.

시스템 설정에서 ‘집계 기준’을 저장된 계획·답변 또는 호출 시도 기록으로 선택한다.
시도 모드에서는 호출 중/응답 관찰·저장 미확정과 결과 저장/미저장/재시작 중단을
표시한다. 이전 서버가 시도 집계를 지원하지 않으면 호환성 오류를 표시한다.
도입 전 메타데이터를 시도로 소급하지 않는다. 세부 시도 페이지 UI와 내보내기는
현재 전용 API로 조회하며 이후 제품 여정으로 추가해야 한다.

## 복구와 보장 한계

기존 SQLite 스키마2의 범용 records를 사용하며 백업/복구에 같이 보존된다.
별도 스키마 번호 변경은 없다. 시작 복구는 `create_app`이 독점 워크스페이스 임대를
얻은 후 100개씩 수행한다. 일반 Store 생성/읽기는 실행 중인 시도를 중단 처리하지 않는다.
반복 시작 복구는 이미 확정/중단된 기록을 다시 변경하지 않는다.

계획/답변 저장과 감사 이벤트 실패 시 committed 전환도 롤백된다. 그 전에 성공한
시도 시작/관찰은 남는다. 미저장 마무리까지 실패하면 observed/started로 남고 재시작
때 interrupted가 된다. 프로세스가 제공자 응답을 받은 직후 관찰 저장 전에 종료되면
해당 사용량은 알 수 없다. 로컬 기록만으로 이 간극을 복원하거나 실제 청구와 동일하게
보장하지 않는다. 로컬 감사 연결의 재작성 한계도 [감사 계약](AUDIT.md)을 따른다.
실제 제공자 청구 대조, 여러 회차 자율 계획, 기록 보존/장시간 부하, 전체 모바일/SR은
전체 v1의 남은 검증 조건이다.
