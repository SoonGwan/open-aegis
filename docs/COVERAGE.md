# 검증 커버리지

커버리지는 승인한 검증 도구를 실행했는지 보여준다. 취약점이 없거나 침입을
차단했다는 보증이 아니다. 현재 카탈로그는 6개 도구이며 워크스페이스 분모는
**활성 자산 수 × 6**이다. 작업 상세와 작업별 보고서는 선택한 자산 × 선택한 도구를
분모로 사용한다. 따라서 작업에서 도구 1개만 완료해도 전체 커버리지는 100%가 되지 않는다.
자산이 없으면 분모는 0이며 콘솔은 비율 대신 ‘—’를 표시한다.

| 결과 | 의미 |
|---|---|
| 미실행 | 아직 승인한 실행 결과가 없거나, 승인 후 이 도구를 시작하지 않음 |
| 실행 중 | 해당 도구 실행 중 |
| 완료 | 도구 수행과 결과 기록을 완료함. 발견 사항이 있어도 완료에 해당 |
| 건너뜀 | 필요한 권한 규칙 등이 없어 해당 도구를 수행하지 않음 |
| 실패 | 연결·기본 응답·도구 수행·결과 기록을 완료하지 못함 |
| 취소 | 중지 또는 승인 거절로 수행하지 못함 |
| 중단 | 서버 재시작으로 실행 결과를 확인할 수 없음 |
| 기록 없음 | 이전 작업의 도구별 결과가 없거나 상태를 해석할 수 없음 |
| 이전 범위 | 실행 당시 자산 revision이 현재 등록 범위와 다름 |

작업 생성과 도구별 미실행 행은 한 SQLite 트랜잭션으로 저장한다.
승인 없이 대상 요청을 보내지 않는다. 기본 응답이 실패하면 선택한 모든 도구에
실패를 남기며, 도구별 건너뜀 이유·오류 종류·시작/종료 시각을 기록한다.
오류 원문과 인증정보는 결과에 넣지 않는다. 중지 또는 서버 재시작은 미완료 행만
취소/중단으로 바꾸며 이미 완료한 증거는 유지한다. 도구별 상태를 확정한 다음
작업의 최종 상태를 게시하므로, 작업 종료 후 미실행 행이 잠시 남는 상태를 피한다.
Planner 내부 실패도 선택한 도구의 실패로 남기며 작업 오류 건수를 1 이상으로 표시한다.

최신 결과는 **자산·도구 각각의 마지막 승인 시각**으로 선택한다. 옛 작업이 늦게
종료되거나 오래된 계획을 나중에 승인하는 경우도 이 순서를 따른다. 승인 시각이
없는 이전 실행 기록은 계획 생성 시각을 사용한다. 같은 시각은 유지되는 행 순서로
구분한다. 승인 대기 또는 거절한 계획은 기존 결과를 대체하지 않는다.
일부 도구만 새로 실행하면 다른 도구의 기존 결과는 유지한다.

자산 수정·보관·복원으로 revision이 바뀌면 이전 승인 범위의 결과는 완료 건수에
포함하지 않는다. 보관한 자산은 워크스페이스 분모에서 제외하지만 작업 상세와
증거 이력은 유지한다. 이전 데이터에 없는 건너뜀/실패 결과를 추정해서 생성하지 않는다.
완료된 이전 작업의 결과 누락은 ‘기록 없음’으로 보여준다.

대시보드·자산 카드·작업 상세·JSON/Markdown 보고서·읽기 전용 MCP 작업 조회에서
같은 결과 계약을 사용한다. 자산 카드의 보관함에서는 과거 완료 검증 종류를 보여주며,
활성 목록은 현재 범위의 최신 완료 건수를 보여준다.
전체 집계는 SQL로 처리하며 응답에 모든 자산의 행렬을 넣지 않는다.

`tests/test_coverage.py`는 승인 전 무요청, 5/6 완료와 건너뜀, 연결 실패, 중지,
revision 변경, 보관/복원, 재시작, 늦게 끝난 이전 실행, 승인 순서, 이전 기록 누락 및
2,000개 자산 × 6개 도구 집계와 응답 크기를 검증한다. 전체 집계 쿼리는 작업→범위→도구→
자산 PK 조회 순서로 실행되도록 SQLite CROSS JOIN 순서를 지정한다. 검수 환경의 동일
fixture에서 수정 전 약 7.3초, 수정 후 약 0.08초였다. 단일 환경 관측값이며 성능 보장은 아니다.
브라우저에서도 로컬 fixture의 새 계획·승인·실행을 거쳐 완료 5개·건너뜀 1개·83%를 확인했다.
