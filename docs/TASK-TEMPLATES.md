# 작업 템플릿

작업 템플릿은 반복 사용할 **계획 기본값**을 저장한다. 템플릿 적용은
현재 자산과 도구 계약으로 새 승인 대기 작업을 만든다. 저장·편집·적용만으로
대상 요청이나 실행 승인을 만들지 않으며 실행은 관리자 승인으로 시작한다.

## 화면

`작업 템플릿`에서 이름·설명·분류와 작업 이름·목표·검사·계획 방식·Worker 수·
검토된 원격 실행 연결을 저장한다. 화면에서 새로 만든 템플릿은 자산을 고정하지
않는다. 적용할 때 현재 자산과 Worker 의존 관계를 선택한다. API로 고정한 기본
자산·의존 관계는 편집 시 유지하며 적용 화면에서 변경할 수 있다.

목록은 이름·설명·분류·목표의 SQL 검색, 활성/보관/전체 필터와25개 페이지를
지원한다. 목록 검색·필터·페이지·삽입 스냅샷은 화면 URL에 저장한다. 템플릿
편집·적용 모달 자체의 URL 복원은 아직 제공하지 않는다.

편집 충돌은409로 거절하며 작성 중인 입력은 남긴다. 현재 템플릿을 조회하고
비교한 뒤 사용자가 현재 버전을 선택하여 작성 내용을 저장할 수 있다. 저장·
적용 중 중복 제출과 닫기를 막는다. 같은 모달의 동일 내용 적용 재시도에는 같은
요청 ID를 사용한다. 새 문서·기기 간 미확인 저장 복원은 구현하지 않았다.

보관은 설정과 이력을 남기며 새 적용만 막는다. 기존 승인 대기 계획과 실행
이력은 유지된다. 복원은 같은 이름의 활성 템플릿과 충돌할 수 있다. 분류는
텍스트 라벨이며 별도 분류 엔티티나 템플릿 실행 예약은 제공하지 않는다.

## 버전과 권한

- 활성 템플릿 이름은 대소문자 구분 없이 유일하다. 최대1,000개를 저장한다.
- 생성은 버전1이다. 편집·보관·복원 시 버전이 증가하며 당시 설정·작성자·행위를
  별도 이력으로 저장한다. 동일 상태 보관 요청은 버전을 추가하지 않는다.
- Viewer는 목록·상세·이력을 읽는다. Operator와 Admin은 저장·편집·보관·적용한다.
  실행 승인은 기존 Admin 정책을 따른다. 커밋 시 현재 역할을 다시 확인한다.
- 적용한 작업은 당시 템플릿 ID·버전·지문·이름·분류·기본 설정·적용 ID를 기록한다.
  이후 편집을 기존 작업에 덮어쓰지 않는다. 재계획·재시도·결과 후속 및 관찰
  파생 계획도 원래 템플릿 출처를 유지한다. 발견 재검증은 별도 발견 출처를 따른다.
- 원격 연결은 적용 시 현재 관리자 등록 계약을 확인하며 승인 직전에도 다시
  검증한다. 템플릿으로 비활성 도구나 변경된 연결의 승인을 우회할 수 없다.

## HTTP

인증과 기존 CSRF 정책을 사용한다. 템플릿 설정은 기존 `TaskInput`과 동일한
필드만 받으며 `status`, `approved_at`, 승인 범위 등 실행 권한 필드는 거절한다.
정규화한 설정과 적용 요청은 각각32KiB JSON 한도와 구조 한도를 검사한다.

| 동작 | 메서드·경로 | 입력 |
| --- | --- | --- |
| 목록 | GET `/api/task-templates` | `limit`1–25, `offset`, `snapshot`, `search`200자, `status` |
| 저장 | POST `/api/task-templates` | `name`, `description`, `category`, `definition`, `request_id` |
| 상세 | GET `/api/task-templates/{id}` | 없음 |
| 편집 | PUT `/api/task-templates/{id}` | `expected_revision`와 이름·설명·분류·설정 |
| 보관·복원 | POST `/api/task-templates/{id}/archive` | `expected_revision`, `archived` |
| 버전 이력 | GET `/api/task-templates/{id}/history` | `limit`, `offset`, `snapshot` |
| 적용 | POST `/api/task-templates/{id}/apply` | `expected_revision`, `request_id`, `overrides` |

`definition`의 자산 목록을 비우면 적용 시 선택하는 휴대 가능한 기본값이다.
Worker 의존 관계를 저장할 때는 실제 기본 자산 목록도 지정한다. 적용 시
`overrides`를 기본값과 합쳐 기존 작업 검증을 수행한다. 비어 있는 적용 자산,
보관 자산·현재 도구 계약 불일치·대기 한도 초과는 계획을 만들지 않는다.

생성 요청 ID는 사용자별로, 적용 요청 ID는 사용자·템플릿별로 범위가 정해진다.
같은 ID·같은 내용은 기존 템플릿/작업을 반환하며 다른 내용은409이다. 이미
성공한 적용의 동일 재시도는 템플릿이 나중에 편집·보관되어도 원래 작업을
반환한다. 이 동작은 새 실행이나 승인 권한을 추가하지 않는다.

설정·버전 이력·감사는 같은 쓰기 트랜잭션이다. 적용은 작업·coverage·적용 영수증·
감사를 함께 저장하며 커밋 시 템플릿·자산·현재 역할을 다시 확인한다. 감사 실패나
검토 중 변경은 전체 계획 저장을 되돌린다.

## 검증과 남은 범위

SQLite와 실제 PostgreSQL에서 템플릿 기능58개 검사가 통과했다. 재계획 시
출처 누락과 큰 적용 요청의 예외 누출은 수정 전 두 저장소에서 실패했고 수정
후 통과한다. 관련 전체·설치 wheel·호스팅 검증은 별도 검증 기록을 따른다.

독립 loopback 자산과 임시 워크스페이스의 실제 화면에서 생성·수정·버전 이력·
보관·복원·적용·승인, 두 탭 동시 편집의409·입력 보존·현재 버전 비교 후 저장을
확인했다. 기존 작업은 버전1 출처를 유지하고 템플릿은 버전6이 되었다. 승인 전
대상 요청0개, 승인 후 GET1개, 감사 무결성 유효를 확인했다. 전체 모바일 여정,
오래된 응답·새 문서 복원·접근성 회귀, 별도 분류 관리와 기존 작업에서 템플릿
저장 기능은 남아 있다. 이 기능만으로 v1 출시 기준을 충족했다고 선언하지 않는다.
