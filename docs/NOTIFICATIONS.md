# 작업 종료 알림 계약

관리자가 고정 수신처를 검토해 채널을 활성화한다. 작업의 완료·실패·중지·서버
중단·승인 거절을 선택한다. 채널 생성은 기본 비활성이며 최대25개, 서버에 등록된
수신처는 최대10개다. 열람자·운영자는 읽기만 가능하다. 저장과 전송 직전에 DB의
현재 관리자 역할과 비활성 여부를 다시 확인한다.

## 수신처 설정

`AEGIS_NOTIFICATION_DESTINATIONS`는 다음 형태의 JSON 배열이다. 실제 주소와
토큰은 별도 환경변수에 둔다. 공개 API·채널 버전·전송 이력에는 해당 값을 저장하지
않는다. 환경변수 이름은 서버 운영자가 설정한다.

```json
[{"id":"operations","name":"운영 알림","endpoint_env":"OPERATIONS_WEBHOOK_URL","token_env":"OPERATIONS_WEBHOOK_TOKEN"}]
```

수신처는 HTTPS이며 사용자 정보·쿼리·fragment를 허용하지 않는다. DNS 주소를
검사·고정하고 사설 주소를 차단하며 리다이렉트는 따라가지 않는다. `lab_http:true`는
운영자가 명시한 리터럴 loopback HTTP 수신처만 허용한다. 토큰은 Bearer 헤더로
보내며 응답 본문은 읽어 보관하지 않는다. 본문은 최대16KiB, 시도는 최대8초다.
인증정보를 바꾸면 이전 승인 지문과 달라져 기존 전송은 차단된다. 채널을 다시 검토해
저장해야 이후 종료 이벤트를 새 설정으로 전송한다. 기존 이력의 수신처를 바꾸지 않는다. PostgreSQL 전송은 실행 소유권 보호 안에서 수행하며, 소유권 연결 상실 중 진행 요청이 끝나기 전 다른 실행 소유자가 인계하지 못하도록 한다.

## 원자적 기록과 전송

작업 종료 상태와 형식이 명확한 알림 원본 이벤트를 같은 트랜잭션으로 저장한다.
이벤트 커서·채널별 전송 대기 기록·감사도 함께 저장한다. 활성화/수정 이후의 이벤트만
대상이며 과거 작업을 소급 전송하지 않는다. 최소 간격은 채널별1–3,600초이며 DB에
다음 전송 가능 시각을 남긴다. 한 채널의 대기열이 다른 채널 전송을 막지 않는다.

네트워크 요청 전에 시도 이력을 저장한다. HTTP 2xx는 **수신처 서버 수락**이다.
사람이 알림을 읽었거나 후속 처리가 완료됐다는 뜻은 아니다. 요청은 같은 전송 ID를
`Idempotency-Key`로 보낸다. 수신처가 이를 지원해야 중복 처리를 줄일 수 있으며
정확히 한 번 처리한다는 보장은 없다.

응답/저장 확인을 잃거나 전송 중 프로세스가 종료되면 `unknown`으로 복구한다.
실패·미확인 기록은 자동 재전송하지 않는다. 관리자가 현재 시도 횟수와 기존 수신처를
검토해 수동 재전송하며 전체 시도는 최대3회다. HTTP 오류나 미확인 결과는 수신처가
이미 처리했을 가능성을 확인해야 한다. 같은 요청 ID의 재시도는 기존 영수증을 반환한다.
화면은 응답 손실 뒤 요청 ID·검토 당시 횟수를 유지하며 목록 갱신으로 바꾸지 않는다.

비활성 채널도 관리자가 현재 버전과 수신처를 별도로 검토해 테스트 알림을 보낼 수
있다. 테스트는 작업 실행/채널 활성화를 바꾸지 않는다. 수정 충돌은 입력을 유지하고
최신 버전을 명시적으로 검토하도록 한다. 채널 버전과 전송 시도는25개 SQL 페이지이며
목록 검색·상태·페이지를 URL에 저장한다.

## API와 범위

- `GET /api/notifications`: 마스킹된 수신처·워커 상태
- `GET/POST /api/notification-channels`, `GET/PUT /api/notification-channels/{id}`
- `GET /api/notification-channels/{id}/history`, `POST /api/notification-channels/{id}/test`
- `GET /api/notification-deliveries`, `GET /api/notification-deliveries/{id}`
- `GET /api/notification-deliveries/{id}/attempts`, `POST /api/notification-deliveries/{id}/retry`

현재는 작업 종료의 JSON webhook 계약이다. 이메일·Slack 전용 형식, 임의 이벤트
필터, 수신처별 큐/보존 정책, 모달·미확인 요청의 새 문서 복원, 전체 모바일·보조 기술,
구버전 실행/백업 복구 검수는 후속 범위다. 고정 수신처 설정은 백업에 포함되지 않으며
운영자가 별도 복구해야 한다. 작업 엔진의 모든 결과 저장을 하나의 트랜잭션으로
만드는 계약은 제공하지 않는다.
