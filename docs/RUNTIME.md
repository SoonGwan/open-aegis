# 실행 제한·대기열·재시도

단일 서버 프로세스에서 같은 origin(스킴·호스트·유효 포트)의 모든 자산과 작업은
요청 속도와 동시 요청 수를 공유한다. 경로가 다르거나 자산을 중복 등록해도
제한이 분리되지 않는다. origin 간에는 독립적으로 진행할 수 있다.
서버가 다중 인스턴스 구성으로 실행되는 경우의 공유 제한은 지원하지 않는다.

## 실행 정책

`.env.example`의 값을 환경변수로 지정하고 서버를 재시작한다. 잘못된 숫자,
범위 밖 값, NaN/무한대는 시작 시 거절한다. 입력 값 자체를 오류에 포함하지 않는다.

| 환경변수 | 기본값 | 허용 범위 | 의미 |
|---|---:|---:|---|
| `AEGIS_TARGET_RPS` | 2 | 0.1–20 | origin별 초당 요청 시작 수, burst 없음 |
| `AEGIS_TARGET_PARALLEL` | 1 | 1–4 | origin별 동시 HTTP 요청 |
| `AEGIS_REQUEST_TIMEOUT` | 8 | 0.1–30초 | 연결·TLS·헤더·본문 전체 HTTP 시간 |
| `AEGIS_DNS_TIMEOUT` | 4 | 0.1–30초 | DNS 대기열과 조회를 합한 시간 |
| `AEGIS_TASK_TIMEOUT` | 300 | 0.2–3,600초 | 작업 시작 후 계획·요청·대기·검증 시간 |
| `AEGIS_QUEUE_TIMEOUT` | 600 | 1–3,600초 | 승인 후 실행 대기 시간 |
| `AEGIS_REQUEST_BUDGET` | 24 | 1–240 | 자산별 실제 HTTP 시도, redirect·retry 포함 |
| `AEGIS_REQUEST_RETRIES` | 1 | 0–2 | 동일 GET의 추가 재시도 횟수 |
| `AEGIS_RETRY_DELAY` | 0.5 | 0.05–10초 | 지수 증가 재시도 기본 대기 |
| `AEGIS_CONCURRENT_TASKS` | 2 | 1–4 | 동시에 실행하는 작업 수 |
| `AEGIS_PENDING_LIMIT` | 30 | 1–100 | 승인 대기·대기열·실행·중지 중 작업 합계 |

작업 생성 시 정책을 저장해 승인 화면에 표시한다. 정책이 바뀐 뒤 기존 계획을
승인하면 409를 반환하며 현재 정책으로 새 계획을 만들어야 한다. 이전 버전의
정책 없는 계획은 승인 시 현재 정책을 기록한다. 기존 승인 범위 revision 검사는 유지한다.

## 시간 초과와 중지

작업 시간은 대기열에서 빠져나오는 시점부터 monotonic clock으로 센다. HTTP 소켓은
전체 요청 시간 제한과 작업 deadline을 함께 검사한다. 소켓 shutdown으로 느린
헤더·본문 및 진행 중 응답을 끊으며 DNS·속도 제한·재시도 대기도 중지할 수 있다.
DNS는 프로세스 공유 daemon worker 4개와 대기열 4개로 제한한다. 시스템 DNS 호출
자체는 강제 종료하지 못하므로 중단된 조회가 그 worker를 점유할 수 있지만, 새
스레드를 늘리거나 서버 종료를 막지 않는다. 대기 중인 새 조회도 DNS deadline에 실패한다.

대기열 감시는 0.25초마다 만료를 확인하고 실행 전 작업을 취소한다. 실행 시간
초과는 작업 `failed`와 `termination_reason=timeout`, 대기열 시간 초과는
`queue_timeout`으로 남긴다. 운영자 중지는 `stopped/operator_stop`이다. 검증 완료
증거는 보존하며 실행하지 못한 검증은 실패 또는 취소로 기록한다. 재검증에서
시간 초과·중지가 발생하면 판정 불가로 남기며 발견 상태를 해결로 바꾸지 않는다.

작업 deadline은 네트워크·대기와 다음 검증을 제어한다. 이미 얻은 응답으로 수행
중인 작은 로컬 계산과 DB 트랜잭션을 강제 종료하지 않는다. 현재 도구의 입력은
응답 128 KiB, 자산 20개, Worker 4개로 제한되며 임의 플러그인/명령은 실행하지 않는다.
소켓 연결 시스템 호출은 지정된 socket timeout으로 제한되므로 중지 요청에는
연결 timeout까지 지연될 수 있다. 일반적인 응답 읽기/대기는 약 20–50ms 간격으로
중지를 확인한다. OS 스케줄링·디스크 장애까지 정확한 종료 시각을 보장하지 않는다.

## 재시도와 재실행

GET의 429/502/503/504, 연결/응답 전송 오류만 정해진 횟수 안에서 재시도한다.
401/403, 범위 위반, 인증서 검증 실패, 사용자 중지, 작업 deadline은 재시도하지 않는다.
`Retry-After` 초 또는 HTTP 날짜를 따르며 60초보다 길면 먼저 재시도하지 않고 그
응답으로 끝낸다. 재시도도 전체 요청 예산·공유 속도·작업 deadline을 사용한다.
응답을 받은 시도와 연결 실패를 각각 트래픽으로 남긴다. `status=0`은 HTTP 응답을
확인하지 못한 시도다. 쿼리·본문·쿠키·요청 인증정보는 트래픽에 저장하지 않는다.
LLM 요청은 별도 승인된 도구 순서 계획이며 자동 재시도·redirect를 하지 않는다.
HTTPS 인증서/DNS 검증과 같은 요청 deadline을 사용한다. 사설 provider는 기본 차단하며
lab에서 `localhost/127.0.0.1/::1`만 허용한다. 제공자에게 키를 보내는 redirect는 금지한다.

`POST /api/tasks/{id}/retry`는 실패·중단·중지된 작업에서 현재 자산 revision과 정책을
담은 새 `pending` 계획을 만든다. 원본과 증거는 유지하고 `retry_of`로 연결한다.
활성 재실행 계획이 있으면 동일 작업을 반환한다. 보관된 자산은 다시 실행할 수 없다.
운영자는 계획만 생성할 수 있으며 실제 실행은 관리자 승인이 필요하다.

## 지표와 종료

인증된 사용자의 `GET /api/runtime`과 시스템 설정 화면은 전체 작업 상태 수,
가장 오래 기다린 작업, 누적 시간 초과, 요청 시도·진행·속도 제한 대기·재시도,
DNS 처리·대기를 표시한다. 작업 수·시간 초과는 DB 전체 기록, 요청 계수는 이번
프로세스 기준이다. 요청 계수는 재시작하면 초기화한다. 대상 호스트·인증정보는
지표에 포함하지 않는다. 대기열 감시 오류는 내용 없이 횟수와 시각만 제공한다.

감시 스레드가 종료되었거나 서버 종료 중이면 health는 503이다. 정상 종료는 새
승인을 막고 실행 중 요청과 대기 작업을 취소한다. `scripts/run.py`와
`python -m aegis` 모두 SSE 연결을 먼저 닫고 Worker 종료를 기다린다.
대기 상태 조회용 SQLite partial index는 저장소 열기 시 멱등적으로 생성한다.

검증: `tests/test_runtime.py`, `tests/test_llm.py`, `tests/test_startup.py`.
실제 loopback 느린 헤더/본문, 공유 간격·슬롯, 중지, DNS 정체, 재시도·예산,
대기열 만료, 정책 변경·재실행, 신뢰 CA TLS·호스트 불일치, HTTPS LLM 계획·사용량,
열린 SSE 연결을 가진 문서화된 실행 스크립트의 SIGTERM을 확인한다.
인터넷 LLM 제공자의 live key, 운영 부하/장시간 soak, 컨테이너 실행은 미검증이다.
