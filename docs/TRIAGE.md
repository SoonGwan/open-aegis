# 발견 사항 조치와 관찰 이력

발견 지문은 자산·검증 도구·결과 코드로 고정된다. 반복 검증은 같은 발견에
증거를 추가하고 담당자·사유·최초 생성 시각을 보존한다.

## 결정과 재검증

관리자와 운영자는 활성 관리자·운영자를 담당자로 지정하거나 해제할 수 있다.
조회자는 조치 기록과 변경 이력을 읽을 수 있지만 변경할 수 없다.
위험 수용에는 수용 사유, 수동 해결 전환에는 해결 사유가 필요하다.
수동 해결은 운영자의 기록이며 검증 성공을 뜻하지 않는다.

- 위험 수용 후 동일 문제가 관찰되거나 재현되어도 수용 결정을 유지한다.
- 해결 뒤 승인한 일반 검증에서 같은 문제가 발견되면 미조치로 재개한다.
  담당자와 이전 해결 사유는 남겨 둔다.
- 일반 검증 승인 이후 사람이 해결 처리했다면 이전 작업은 관찰 증거만 추가한다.
- 재검증은 계획 생성 시 조치 버전을 저장한다. 판정 시 버전이 바뀌었으면
  재현·해결 결과는 남기고 최신 조치 상태를 덮어쓰지 않는다.
- 판정 불가는 기존 상태를 유지한다. 기준 버전이 없는 이전 재검증도 자동 변경하지 않는다.
- 동일 발견의 진행 중 재검증 계획을 동시에 요청하면 같은 작업을 반환한다.

## API와 기록

`PATCH /api/findings/{id}`에는 `expected_revision`(1 이상)이 필수다.
선택 필드는 `status`, `assignee_id`(null은 해제), `acceptance_reason`,
`resolution_reason`이며 사유는 4,000자로 제한한다. 생략한 필드는 보존한다.
기준 버전 불일치는 409, 잘못된 담당자·사유는 422다. 동일 값 저장은 버전이나
이력을 늘리지 않는다. 이전 발견의 최초 조치 버전은 1이다.

`GET /api/assignees`는 활성 관리자·운영자의 공개 정보만 반환하며 검색·페이지를
지원한다. `GET /api/findings/{id}/history`는 25개 기본 페이지와 snapshot 워터마크를
지원한다. actor, 변경 전후 값, 사유, 연결 작업·증거·재검증 ID를 저장한다.
발견·증거·이력은 한 SQLite 트랜잭션에 기록한다. JSON 보고서는 선택한 발견의
전체 조치 이력을 포함하며 Markdown은 현재 담당자와 사유를 포함한다.

이전 버전의 변경 이력은 소급 생성하지 않는다. 이력은 일반 DB 기록이며
암호학적 변조 증명이나 외부 감사 보관을 제공하지 않는다. 전체 보고서 및 발견
상세의 증거·재검증 목록은 아직 스트리밍/페이지네이션을 완료하지 않았다.
