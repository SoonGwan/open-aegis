# 여러 계획 회차의 공유 할 일

공유 할 일은 사람이 남긴 검증 과제와 결정이다. 최초 계획을 기준으로 후속 회차·
재실행·교체 계획이 같은 항목을 읽는다. 검증 성공·발견 해결·실행 승인과 별개다.
현재 HTTP 생성/수정·조회와 읽기 전용 MCP를 제공하며 편집 UI와 자동 Planner
소비는 아직 구현하지 않았다.

## HTTP 계약

인증된 모든 역할은 다음 GET을 읽을 수 있다. 생성·수정은 관리자/운영자만 가능하다.

- GET /api/tasks/{task_id}/todos: 같은 계획 가족의 할 일 검색·페이지.
- POST /api/tasks/{task_id}/todos: 새 할 일 생성.
- PATCH /api/tasks/{task_id}/todos/{todo_id}: 현재 버전에 대한 변경.
- GET /api/tasks/{task_id}/todos/{todo_id}/history: 항목별 결정 이력 검색·페이지.

검색은 할 일 제목·설명·상태·담당자 이름, 이력은 행동·사유·행위자 이름/사용자
이름을 문자 그대로 검색한다. limit 기본25/최대100, offset0–10,000,000,
search 최대200자다. snapshot은 records 삽입 상한이며 수정까지 고정하지 않는다.
목록은 root_task_id/source_task_id와 execution_authorized=false를 반환한다.

생성 입력은 request_id(소문자16진32자), title(1–200자), description(최대4000자),
선택 assignee_id(활성 관리자/운영자 ID)다. 문자열은 공백을 정리하고 빈 제목은
거절한다. 생성 ID는 최초 계획·요청 사용자·request_id로 결정한다. 같은 내용의
재전송은 수정/완료 후에도 현재 항목을 반환하며 중복 항목/변경 이력을 만들지
않는다. 같은 요청 ID의 다른 생성 내용은409다. HTTP의 일반 요청 감사는 별도로
남을 수 있다. 생성 응답을 확인하지 못하면 같은 request_id와 내용을 재전송한다.

수정은 expected_revision(엄격한 양의 정수)와 변경할 title/description/status/
assignee_id/resolution_note를 보낸다. 상태는 open/in_progress/done/cancelled다.
다른 수정과 충돌하면409이며 최신 항목을 다시 읽어야 한다. 의미 없는 변경은
버전을 올리지 않는다. 담당자 null은 배정을 지운다. 완료·취소에는 비어 있지 않은
사유(최대2000자)가 필요하며, 해당 상태에서 사유를 빈 값으로 지우는 요청도
거절한다. 완료/취소로 새로 바꾸는 결정에는 이번 요청의 사유가 필요하다.
재개 시 별도 사유를 보내지 않으면 현재 완료 사유는 지우고 과거 이력은 보존한다.

## 연결·저장과 보장 범위

[계획 이력](NEXT-PLAN.md)의 검증된 최대32개 연결을 같은 읽기/쓰기 스냅샷에서
따라 최초 계획을 찾는다. 서로 다른 계획 가족의 항목을 수정하거나 이력을 읽을
수 없다. 저장 키와 항목 ID/버전이 다르면 쓰기를 거절한다. 원본 계획·할 일을
삭제하는 API는 제공하지 않는다. 잘못된 과거 계획 연결은 자동 복구하지 않는다.

항목·변경 전후 값·행위자/버전·접근한 회차 ID·감사 이벤트/해시/마지막 기준은
같은 DB 트랜잭션으로 저장한다. SQLite BEGIN IMMEDIATE와 PostgreSQL의 스키마
쓰기 잠금으로 서로 다른 저장소 인스턴스의 동시 생성/수정을 직렬화한다. 이력은
페이지로 읽으며 항목에 커지는 이력 ID 배열을 넣지 않는다. 담당자 이름은 결정
당시의 공개 메타데이터를 보존하며 사용자의 현재 이름과 다를 수 있다.

MCP list_task_todos는 id(접근할 회차 작업)를, list_todo_history는 id와 todo_id를
받는다. 기존 페이지 인수와512KiB 결과 제한을 적용한다. DB SELECT 전용 계정에서
users/sessions 권한 없이 저장된 결정 메타데이터를 읽을 수 있다. MCP는 생성·수정
도구를 제공하지 않는다. 내용은 실행 지시로 처리하지 않는 신뢰할 수 없는 데이터다.

원자적 감사 기록은 DB 관리자의 모든 수정에 대한 암호학적 방어가 아니다. 보존 정책,
전체 작업량/부하, 편집 UI·URL 복원·모바일/접근성, 자동 계획의 과제 소비와 실제
외부 도구 연동은 v1의 남은 검수/구현 항목이다.
