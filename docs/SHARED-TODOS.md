# 여러 계획 회차의 공유 할 일

공유 할 일은 사람이 남긴 검증 과제와 결정이다. 최초 계획을 기준으로 후속 회차·
재실행·교체 계획이 같은 항목을 읽는다. 검증 성공·발견 해결·실행 승인과 별개다.
HTTP 생성/수정·조회, 작업 상세의 편집 UI와 읽기 전용 MCP를 제공한다.
미완료·진행 중 항목의 명시적 도구 요청을 다음 계획에 반영한다. [이벤트 처리기](EVENT-PLANNER.md)가 변경을 읽어 제안을 자동 준비한다. 자유 문장의
목표 분해는 아직 구현하지 않았다.

## HTTP 계약

인증된 모든 역할은 다음 GET을 읽을 수 있다. 생성·수정은 관리자/운영자만 가능하다.

- GET /api/tasks/{task_id}/todos: 같은 계획 가족의 할 일 검색·페이지.
- POST /api/tasks/{task_id}/todos: 새 할 일 생성.
- GET /api/tasks/{task_id}/todos/{todo_id}: 같은 가족의 현재 항목 조회.
- PATCH /api/tasks/{task_id}/todos/{todo_id}: 현재 버전에 대한 변경.
- GET /api/tasks/{task_id}/todos/{todo_id}/history: 항목별 결정 이력 검색·페이지.

검색은 할 일 제목·설명·상태·담당자 이름, 이력은 행동·사유·행위자 이름/사용자
이름을 문자 그대로 검색한다. limit 기본25/최대100, offset0–10,000,000,
search 최대200자다. snapshot은 records 삽입 상한이며 수정까지 고정하지 않는다.
목록은 root_task_id/source_task_id와 execution_authorized=false를 반환한다.

생성 입력은 request_id(소문자16진32자), title(1–200자), description(최대4000자),
선택 assignee_id(활성 관리자/운영자 ID), check_ids(내장 검증 ID 목록, 최대6개)다.
알 수 없는 도구와 중복 ID는 거절하고 카탈로그 순서로 저장한다. 생략은 빈 목록이며
이전 버전의 도구 필드 없는 생성 요청도 같은 요청 ID로 재전송할 수 있다. 문자열은 공백을 정리하고 빈 제목은
거절한다. 생성 ID는 최초 계획·요청 사용자·request_id로 결정한다. 같은 내용의
재전송은 수정/완료 후에도 현재 항목을 반환하며 중복 항목/변경 이력을 만들지
않는다. 같은 요청 ID의 다른 생성 내용은409다. HTTP의 일반 요청 감사는 별도로
남을 수 있다. 생성 응답을 확인하지 못하면 같은 request_id와 내용을 재전송한다.

수정은 expected_revision(엄격한 양의 정수)와 변경할 title/description/status/
assignee_id/resolution_note/check_ids를 보낸다. 상태는 open/in_progress/done/cancelled다.
다른 수정과 충돌하면409이며 최신 항목을 다시 읽어야 한다. 의미 없는 변경은
버전을 올리지 않는다. 담당자 null은 배정을 지운다. 완료·취소에는 비어 있지 않은
사유(최대2000자)가 필요하며, 해당 상태에서 사유를 빈 값으로 지우는 요청도
거절한다. 완료/취소로 새로 바꾸는 결정에는 이번 요청의 사유가 필요하다.
재개 시 별도 사유를 보내지 않으면 현재 완료 사유는 지우고 과거 이력은 보존한다.

## 연결·저장과 보장 범위

[계획 이력](NEXT-PLAN.md)의 검증된 최대32개 연결을 같은 읽기/쓰기 스냅샷에서
따라 최초 계획을 찾는다. 서로 다른 계획 가족의 항목을 수정하거나 이력을 읽을
수 없다. 저장 키와 항목 ID/버전이 다르면 쓰기를 거절한다. 원본 계획·할 일을
삭제하는 API는 제공하지 않는다. 잘못된 과거 계획 연결은 자동 복구하지 않는다.

항목·변경 전후 값·행위자/버전·접근한 회차 ID·감사 이벤트/해시/마지막 기준은
같은 DB 트랜잭션으로 저장한다. SQLite BEGIN IMMEDIATE와 PostgreSQL의 스키마
쓰기 잠금으로 서로 다른 저장소 인스턴스의 동시 생성/수정을 직렬화한다. 이력은
페이지로 읽으며 항목에 커지는 이력 ID 배열을 넣지 않는다. 담당자 이름은 결정
당시의 공개 메타데이터를 보존하며 사용자의 현재 이름과 다를 수 있다.

MCP list_task_todos는 id(접근할 회차 작업)를, list_todo_history는 id와 todo_id를
받는다. 기존 페이지 인수와512KiB 결과 제한을 적용한다. DB SELECT 전용 계정에서
users/sessions 권한 없이 저장된 결정 메타데이터를 읽을 수 있다. MCP는 생성·수정
도구를 제공하지 않는다. 내용은 실행 지시로 처리하지 않는 신뢰할 수 없는 데이터다.

원자적 감사 기록은 DB 관리자의 모든 수정에 대한 암호학적 방어가 아니다. 보존 정책,
전체 작업량/부하, 전체 모바일/접근성, 의미적 목표/관찰 소비와 실제
외부 도구 연동은 v1의 남은 검수/구현 항목이다.


## 작업 상세 화면

인증된 작업 상세에서 제목·설명·담당자 검색/페이지·상태·완료/취소 사유를 편집한다.
조회자는 목록과 항목별 변경 이력을 읽는다. 목록/이력은 각각25개 페이지와 검색을
사용하며 조회 실패를 빈 결과로 표시하지 않는다. 선택한 상세는 마지막 조회 당시의
기록이다. 최신 상태는 목록에서 다시 선택하거나 편집 충돌의 현재 항목 조회로 확인한다.

생성 요청은 전송 전에 같은 탭의 sessionStorage에 사용자·접근 회차별로 저장한다.
저장소를 사용할 수 없으면 전송하지 않는다. 성공 응답이 없으면 입력을 잠그고
같은 요청 ID/내용으로 재시도한다. 새로고침/상세 재진입에도 미확인 요청을 복원한다.
서버422로 거절된 생성은 재시도 정보를 정리하고 내용을 수정할 수 있다. 통신 오류나
503 등 결과가 불명확한 요청은 유지한다. 확정 응답도 이전 세션이면 현재 화면에
적용하지 않는다. 저장 확인 후 정보 정리에 실패하면 같은 요청 확인을 유지한다.
다른 기기·새 탭 복원이나 전송 전 초안의 영속 보관은 제공하지 않는다.

편집 중 목록 갱신은 초안을 덮어쓰지 않는다.409 충돌 후 초안을 유지하며 최신
기록 조회·비교를 제공한다. 사용자가 선택하면 자신의 변경 필드만 최신 기준으로
다시 준비하거나 입력을 버리고 현재 기록으로 시작한다. 준비 후에도 명시적 저장과
버전 검사를 거친다. 동일 필드를 다른 사람이 바꾼 경우 내 변경 선택은 해당 필드에
내 값을 적용하겠다는 결정이다. 완료/취소 사유와 과거 이력은 별도로 확인한다.

할 일 검색·페이지·선택/이력 위치는 URL에 보존한다. 저장 중 입력은 잠기며 버튼
연속 제출을 방지한다. 탐색/세션 교체 후 늦은 완료는 새 선택/편집 초안을 초기화하지
않는다. 같은 사용자·작업의 생성 폼이 아직 열려 있으면 확인된 요청의 잠금을 풀고
앞서 보낸 요청의 완료를 안내한다. 실제 모바일 터치/줌과 스크린리더 검수는 남아 있다.

## 탐색 URL

- task_todos_q/offset/snapshot: 목록 검색·25개 페이지·삽입 상한.
- task_todo_id: 선택한 할 일. 현재 항목은 별도 GET으로 조회하며 실패 시 재조회한다.
- task_todo_history_q/offset/snapshot: 해당 항목 변경 이력의 독립 검색·페이지·삽입 상한.

작업 상세에서만 읽으며 ID는 영문/숫자/밑줄/하이픈1–80자로 제한한다. 검색은200자,
offset은0–10,000,000 범위의25개 배수로 정규화하고 snapshot은 브라우저의 안전한
정수 범위를 사용한다. 잘못된 ID를 API 경로에 넣지 않는다. 존재하지 않는 유효한
ID는 서버404를 표시하고 닫기/재조회할 수 있다. 항목 조회 실패를 빈 목록으로
표시하지 않는다. 항목/이력 페이지 로드 실패는 별도로 안내한다.

검색을 바꾸면 해당 목록의 위치만 초기화한다. 항목을 바꾸거나 선택을 닫으면 이력
조건을 지우고 목록 검색/페이지는 유지한다. 작업 상세를 닫거나 다른 작업으로 바꾸면
모든 할 일 탐색 상태를 지운다. 이전/다음 탐색 및 같은 북마크의 새 문서 열기는
독립 위치와 선택을 복원한다. 이전 항목의 늦은 페이지 콜백은 새 항목의 URL에
조건을 쓰지 못한다. 편집 중 이력/목록 탐색은 같은 항목의 초안을 덮어쓰지 않는다.
편집 열림 상태/전송 전 초안은 URL에 저장하지 않으며 다른 항목으로 바꾸면 닫힌다.
저장 후 목록/이력은 검색·offset을 유지하고 snapshot을 풀어 새 기록을 읽는다.

## 계획에 반영하는 요청

미완료·진행 중 항목의 check_ids를 결과 기반 다음 계획의 추가 후보로 합친다.
이미 완료된 검증도 명시적 요청으로 다시 제안할 수 있으며 반복 근거를 표시한다.
완료·취소 항목은 도구를 요청하지 않는다. 할 일의 완료는 실제 실패 커버리지를
지우거나 검증 성공으로 바꾸지 않는다. 설명만 작성해도 새로운 도구를 선택하는
의미 해석 기능은 제공하지 않는다. 자산 범위·도구 계약·회차 제한·새 승인은 유지한다.

후속·교체·재실행 계획은 생성 시점의 공유 항목 ID/버전/상태/제목/설명/도구 요청/
결정 사유를 shared_todo_context에 저장한다. 가족의 현재 항목 전체를 같은 DB
스냅샷에서 검증하며 최대100개·정규 JSON UTF-8 64KiB를 넘으면 계획을 거절한다.
일부 항목만 조용히 사용하는 방식은 없다. 할 일 생성 자체는100개 제한이 아니므로
큰 가족은 정리·분리해야 한다. 계획 조회 후 저장 전 변경은409이며, 최종 재검증과
후속 계획·원본 연결·커버리지·생성 이벤트 저장은 같은 쓰기 트랜잭션이다.

이미 저장된 계획은 이후 할 일 편집으로 바뀌지 않는다. 재계획은 현재 맥락을 다시
저장하지만 기존 선택 도구를 유지한다. UI에서 계획 당시 항목과 버전을 확인한다.
규칙 Planner는 저장된 활성 요청 도구를 승인된 목록 안에서 앞에 둔다. AI Planner는
활성 항목의 id/revision/status/title/description/check_ids와 맥락 지문만 설정된
제공자에게 보낸다. 담당자·사용자 이름·종료 사유는 보내지 않는다. 사람의 문장은
신뢰할 수 없는 데이터이며 도구 추가/명령/URL 실행 권한이 아니다. 제공자 답변은
승인된 도구 목록의 정확한 순열이어야 하며 잘못된 응답은 규칙 순서로 돌아간다.
자동 이벤트 처리기는 해당 맥락의 제안을 준비한다. 상용 제공자 호출 검수와
의미적 목표 분해/관찰 소비는 남아 있다.
