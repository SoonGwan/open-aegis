# 이벤트 기반 다음 계획 준비

서비스는 기본으로 감사 이벤트 순서를 읽어 결과 기반 후속 제안을 준비한다.
대상 요청·LLM 호출·작업 생성·승인은 수행하지 않는다. 자동으로 준비된 제안도
사용자가 검토해 새 승인 대기 계획으로 반영하고 관리자가 별도로 승인한다.

## 이벤트와 맥락

작업 이벤트에서는 검증된 과거 연결과 현재 후속/교체/재실행을 따라 승인된 종료
작업의 제안을 갱신한다. 따라서 원본 회차에서 편집한 공유 할 일도 현재 종료
후속 회차의 제안에 반영한다. 자산 ID가 있는 전역 이벤트는 해당 자산의 작업을
SQL25개 페이지로 읽어 갱신한다. 실행 중·승인 전 작업의 도구는 바꾸지 않는다.
일반 자산 등록/수정/보관/복원, 종료·대기 시간 초과·서버 종료 중지와 공유 할 일
변경을 처리한다. 원본 이벤트 전체 내용을 제공자에게 보내지 않는다.

저장된 plan_reviews에는 원본 작업, 이벤트 순번, 준비 시각, 상태와 제안 지문/
항목 버전/범위/도구 계약을 포함한 제안이 있다. ready는 검토할 제안이 있다는
뜻이며 no_proposal은 추가 후보 없음·이미 연결됨·한도 도달 등이다. blocked는
잘못된 연결/범위/할 일로 준비를 거절한 상태다. 안전성 판정이 아니다.

## 재시작과 원자성

planner_state/event-planner에 마지막 처리 이벤트와 자산 페이지 offset/snapshot,
정책 지문을 저장한다. 한 쓰기 트랜잭션에서 제안과 처리 위치를 함께 저장한다.
실패하면 둘 다 롤백하고 같은 위치를 재시도한다. 한 단계는 최대25개 이벤트의
연속 구간 또는 자산 작업25개다. 같은 구간의 반복 작업 이벤트는 마지막 순번으로
한 번 준비하며 작업별 마지막 순번의 순서대로 반영한다. 제안은 현재 저장 상태를
읽으므로 과거 payload를 순서대로 실행하지 않는다. 감사 원본 이벤트는 삭제하거나
합치지 않는다. 자산 변경 이벤트 앞에서 구간을 끊고 해당 자산의 전체 페이지를
처리한 뒤 후속 이벤트를 처리한다. 완료 전 페이지 위치도 보존해 재시작 후 이어서 처리한다.
대기 중에는 읽기만 수행하고 쓰기 잠금을 반복해서 잡지 않는다.

초기 실행은 기존 이벤트를 재생한다. 실행 정책이 바뀌면 이벤트를 처음부터
재생해 현재 정책의 제안을 준비한다. 종료 시 처리기를 먼저 중지한 뒤 Engine을
종료하므로 마지막 종료 이벤트는 다음 시작 때 처리할 수 있다. SQLite 워크스페이스
소유권/네이티브 PostgreSQL 런타임 소유권을 유지하며 DB 장애/소유권 상실은 기존
저장소 계약을 따른다. 잘못된 계획은 blocked로 분리하고 다음 이벤트를 처리한다.
일시적 저장 오류는 위치를 건너뛰지 않는다. 저장된 처리 위치가 손상되면 자동
복구로 추측하지 않으며 오류 지표를 확인해야 한다.

## 읽기와 검토

인증된 모든 역할은 GET /api/tasks/{id}/planner로 저장된 준비 상태를 읽는다.
제안의 현재 지문을 읽기 스냅샷에서 비교해 stale을 표시하며 조회만으로 저장
제안을 고치거나 새 계획을 만들지 않는다. 아직 준비되지 않은 항목은 waiting,
존재하지 않는 작업은404다. GET /api/runtime의 event_planner는 처리기 생존 상태,
프로세스 오류 수·마지막 오류 시각을 제공한다.

상세 화면은 준비 상태를4초마다 읽는다. 조회 실패는 실패로 안내하며 명시적
재조회 버튼을 제공한다. 화면을 닫으면 요청/예약을 중단하고 이전 응답을 적용하지
않는다. 표시 중인 제안과 새 이벤트 제안의 지문이 다르면 다시 조회하도록 안내한다.
실제 반영은 [다음 계획](NEXT-PLAN.md)의 최신 지문과 최종 쓰기 재검증을 그대로
거치므로 저장된 자동 제안이 승인 권한이 되지 않는다.

## 남은 범위

자유 문장의 목표 분해, Worker 관찰에 대한 의미 판단/도구 실행, 실행 중 AI 개입,
실제 상용 모델, 전체 이벤트량의 장시간 처리 지연/자원 SLO, 보존 정책과 전체
모바일·보조 기술 여정은 미완료다. 실제 승인 실행·조회와 프로세스 장애를 함께
검수하는 [리허설](EXECUTION-LOAD.md)은 운영 SLO 판정을 대신하지 않는다.
모든 전역 이벤트가 자산 ID를 포함하는 것은
아니므로 제공자 가격·사용자/노트 등 전역 변경을 도구 요청으로 해석하지 않는다.
DB에 직접 넣은 기록에는 이벤트가 없을 수 있으며 별도의 자동 감지 기능은 없다.
커서/지문은 내부 일관성 검사로 DB 관리자에 대한 암호학적 방어가 아니다.
