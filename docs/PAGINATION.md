# 목록 조회 계약

인증된 계정은 `GET /api/records/{kind}`로 `assets`, `tasks`, `findings`,
`traffic`, `notes`, `schedules`, `observations`를 조회한다. 사용자·인증 설정·세션은 이 경로에서 제공하지 않는다.
조회 역할도 목록을 읽을 수 있으며 변경 권한은 기존 API에서 별도로 검사한다.

- `limit`: 기본 25, 최대 100. `offset`: 기본 0, 최대 10,000,000.
- `search`: 최대 200자. 각 종류의 이름·주소·소유자 등 공개 필드를 SQL로 검색한다.
  `%`, `_`, 따옴표는 와일드카드나 SQL 명령이 아닌 문자로 취급한다.
  SQLite 기본 `lower()`의 영문 대소문자 변환을 사용하며 전체 Unicode case folding은 지원하지 않는다.
- `status`, `severity`, `asset_id`, `task_id`: 일치 필터.
  작업의 자산과 발견의 작업은 JSON 배열의 원소를 비교한다.
- `archived`: 자산에만 사용할 수 있다. 생략하면 보관 여부를 모두 포함한다.
  콘솔은 활성/보관함을 명시적으로 구분한다.
- 노트는 제목·내용, 예약은 `task.name`·`task.goal`을 검색한다.
  예약의 `asset_id`는 `task.asset_ids` 배열에서 비교한다.
  `enabled=true/false`는 예약 전용 활성 필터이며 다른 종류에 사용하면 422다.
- 관찰은 URL·제목·자산 ID·작업 ID와 현재 자산/작업 이름을 검색한다.
  `asset_id`, `task_id`를 정확히 일치하는 출처 필터로 사용할 수 있다.
  응답의 `asset_name`, `task_name`은 현재 메타데이터이며 과거 이름의 스냅샷이 아니다.
  출처가 사라진 관찰은 보존하고 이름을 null로 반환한다. 보관된 자산의 관찰도 포함한다.

응답은 `items`, `total`, `limit`, `offset`, `snapshot`, `has_more`를 포함한다.
`total`은 해당 필터와 삽입 상한에 포함되는 전체 건수이며 현재 페이지 길이가 아니다.
첫 조회에서 받은 `snapshot`을 다음 조회에 보내면 그 이후에 삽입된 행은 제외된다.
수정 시 UPSERT로 기존 행 순서를 유지한다. 기존 기록의 수정·삭제·필터 변경은
실시간으로 반영되므로 이 값은 과거 내용을 고정한 데이터베이스 스냅샷이 아니다.
콘솔의 ‘최신 목록’은 첫 페이지에서 삽입 상한을 새로 잡는다.

콘솔은 검색 입력을 250ms 지연해서 요청하고 이전 요청을 취소한다.
늦게 도착한 응답은 다른 검색·페이지 결과를 덮어쓰지 않는다.
작업과 예약 생성의 자산 선택기는 다른 페이지로 이동해도 최대 20개 선택을 유지하며,
선택한 전체 ID를 숨은 폼 필드로 제출한다. 서버가 승인 범위와 자산 상태를 다시 검증한다.

## 콘솔 URL과 조회 상태

자산·작업·발견·트래픽·승인·보고서·노트·예약·관찰 화면은 각각 `assets`, `tasks`, `findings`,
`traffic`, `approvals`, `reports`, `notes`, `schedules`, `observations` 접두사를 사용한다. `${page}_q`, `${page}_offset`,
`${page}_snapshot`으로 검색과 위치를 보존한다. `tasks_status`, `findings_severity`,
`assets_archived=true`, `schedules_enabled=true/false`는 화면별 필터다. 다른 화면과 `graph_*` 북마크 값은 유지한다.
검색은 현재 이력을 교체하고 화면·필터·페이지 이동은 새 이력을 추가한다.
브라우저 뒤로/앞으로와 콘솔의 ‘이전 탐색’/‘다음 탐색’은 같은 이력을 사용한다.
콘솔 버튼은 앱에서 시작한 이력 범위 안에서만 활성화한다.

첫 페이지는 삽입 상한 없이 최신 결과를 조회한다. 다음 페이지로 이동하면 응답의
삽입 상한을 URL에 기록한다. 검색·필터 변경은 첫 페이지와 새 삽입 상한으로 시작한다.
변경 저장 후에는 검색·필터·위치를 유지하며 삽입 상한을 비운다. 새 계획·재검증·재실행
생성 후에는 이전 승인 검색에 가려지지 않도록 승인 목록을 초기화한다.
노트·예약 생성도 해당 화면의 검색·필터·위치를 초기화해 새 기록을 표시한다.
전체 건수가 줄면 마지막 유효 페이지로 위치를 교체하며 빈 결과는 첫 페이지로 돌아간다.
다른 경로로 이동한 뒤 도착한 응답은 현재 URL을 수정하지 못한다.

검색은 200 UTF-16 코드 단위, offset은 0–10,000,000 범위의 25 배수,
snapshot은 JavaScript 안전 정수로 제한한다. 잘못된 필터와 숫자는 기본값으로 정규화한다.
새 검색의 조회 중·실패 상태와 정상적인 빈 결과를 구분한다. 기존 결과를 갱신하다
실패하면 마지막 목록임을 표시하고, 오류 시 재조회 버튼과 한국어 연결 안내를 제공한다.
조회는 4초마다 자동 갱신한다. 상세 모달은 URL에 기록하지 않으며 이력 이동 시 닫는다.
증거 상세 모달의 목록 상태는 URL 계약에 포함하지 않는다.

`/api/overview`의 배열은 종류별 최근 100개로 제한하지만 통계와 심각도 분포는
전체 기록을 SQL로 집계한다. 자산 카드의 과거 완료 검증 종류도 해당 자산의 전체
이력에서 집계한다. 활성 자산은 현재 revision의 최신 승인 결과를 별도로 집계한다.
실패·건너뜀과 분모의 의미는 [COVERAGE.md](COVERAGE.md)에 정의한다.
탐색 경로 화면은 자산과 작업을 선택한 실제 관계 그래프이며 별도의 SQL 페이지와
결과 상한을 사용한다. [GRAPH.md](GRAPH.md)에 조회 범위와 연결 조건을 정의한다.

기존 배열 경로 `/api/assets`, `/api/tasks`, `/api/findings`, `/api/traffic`, `/api/notes`, `/api/schedules`는
최대 1,000개를 반환하며 `X-Total-Count`, `X-Results-Limited` 헤더로 전체 건수와
잘림 여부를 알린다. 전체를 순회하는 클라이언트는 페이지 경로를 사용해야 한다.
보고서 등 일부 내부 처리의 무제한 조회는 후속 작업으로 남아 있다.
`overview.stats.observations`는 최근 100개 요약과 별도로 전체 관찰 수를 집계한다.
자산 화면의 워크스페이스 관찰 미리보기는 최근 30개를 표시하며 ‘전체 관찰 링크’는
검색·페이지를 초기화한 관찰 화면으로 이동한다. 일반 메뉴 이동은 이전 상태를 유지한다.
관찰 화면은 URL을 텍스트로 표시하며 대상에 HTTP 요청하지 않는다. 관찰은 HTML의
범위 내 링크 수집 결과이며 접근 가능성이나 취약점 판정을 뜻하지 않는다.
예약 처리기는 전체 목록 대신 실행 시각이 지난 활성 예약을 최대 100개씩 읽는다.
`next_at`과 rowid 오름차순으로 오래 기다린 예약을 먼저 처리하며, 다음 루프는 5초 후다.
예약으로 생성한 작업도 승인 대기 상태이며 HTTP 검증을 자동 실행하지 않는다.

## 발견 상세의 증거·재검증 이력

`GET /api/findings/{finding_id}/evidence`와 `/retests`는 같은 페이지 응답 구조와
limit(기본 25, 최대 100)·offset·snapshot·search 경계를 사용한다. 인증이 필요하며
조회 역할도 접근할 수 있다. 없는 발견은 404, 다른 collection과 잘못된 경계는 422다.
증거는 도구 ID·작업 ID, 재검증은 판정 코드·사유·작업 ID를 문자 그대로 검색한다.
이력은 최신 삽입 순서이며, 수정은 현재 값으로 반영하고 다음 페이지에는 삽입 상한을 유지한다.

증거는 발견의 `evidence_ids`에 속하면서 자산·검증 도구·지문이 같고 작업 ID가
발견의 `task_ids`에 속해야 한다. 중복 참조는 한 번만 반환하고, 없거나 관계가 맞지
않는 참조는 제외한다. 지문이 없는 이전 증거도 이 검증을 통과하지 못하면 제외한다.
재검증은 저장된 `finding_id`로 조회한다. 임의의 증거 종류를 공용 records API에
추가하지 않으며, 발견을 기준으로 해당 이력만 조회한다.

기존 `GET /api/findings/{finding_id}`의 evidence·retests 배열은 각각 최신 25개까지
반환한다. `evidence_page`, `retests_page`에 전체 건수·삽입 상한·추가 페이지 여부를
제공한다. 예전의 전체 배열을 기대하는 클라이언트는 새 페이지 경로로 이동해야 한다.
HTTP `/api/overview`, `/api/records/findings`, `/api/findings`, `/api/findings/{id}`의
발견 메타데이터는 SQL에서 `task_ids`, `evidence_ids`를 제외하고 `task_count`,
`evidence_reference_count`, `related_ids_omitted=true`를 반환한다. 조치 PATCH 응답도
같은 요약을 반환한다. PATCH는 다시 조회하지 않고 방금 저장한 결정의 버전과 상태를
요약하므로, 뒤이어 들어온 다른 사람의 결정을 저장 응답으로 바꾸지 않는다.
내부 저장·검증·보고서에 필요한 전체 연관 배열은 변경하지 않는다. 기존 클라이언트는
증거/재검증 페이지의 작업 ID와 개수를 사용해야 한다. 참조 수에는 중복·누락 참조도
포함될 수 있으며, 출처를 검증한 실제 증거 수는 evidence 페이지의 total이다.
서비스 경로의 Store.all 호출은 제거했다. 재시작 복구는 미완료 작업을 100개씩
읽고, 자산 중복·실행/이력 존재 여부는 SQL의 단일 존재 조회를 사용한다. 그렇더라도
단일 payload·연관 ID 배열·SQLite 자원까지 서비스 전체의 응답/메모리 상한이
확보됐다는 의미는 아니다. MCP도 관련 ID를 SQL에서
개수로 요약하고 이력을 페이지로 반환한다([MCP.md](MCP.md)).

콘솔은 각 이력을 펼쳤을 때 검색·페이지 조회를 시작한다. 접으면 갱신을 멈추며,
열려 있는 동안은 4초마다 갱신한다. 각각의 검색과 위치는 서로 독립적이다.
모달 안의 위치는 URL에 보존하지 않으며 모달을 닫으면 초기화한다.
조회 중·조회 실패·정상 빈 결과는 공통 목록 상태 표시를 사용한다.

검증 기록: `tests/test_records.py`는 15,000개 기록, 전체 건수, 응답 크기 제한,
삽입·수정 중 순서 유지, 문자 그대로 검색, 배열 필터, 비공개 종류와 범위 거부,
요약 제한 이후에도 정확한 심각도와 자산별 과거 검증 건수를 검사한다.
브라우저에서 격리된 31개 fixture 자산의 페이지 이동과 두 페이지의 자산을 선택한
계획 저장을 확인했다. 계획은 승인 대기 상태이며 대상 HTTP 요청은 0개였다.
이 검증은 장시간 운영 부하나 PostgreSQL 지원을 증명하지 않는다.


## 작업 상세의 발견·실행 기록

`GET /api/tasks/{task_id}/findings`와 `/events`는 인증된 모든 역할이 읽을 수 있는
페이지 경로다. 기본 25개·최대 100개, offset·snapshot·search(최대 200자)를 받는다.
없는 작업은 404, 잘못된 경계는 422다. 발견은 해당 작업에 연결된 기록만 반환하고
관련 ID 배열을 개수로 요약한다. 실행 기록은 해당 작업의 메시지·수준을 문자 그대로
검색하며 detail JSON은 검색하지 않는다. 두 목록 모두 최신 삽입 순서다.

기존 `GET /api/tasks/{task_id}`의 findings·events 배열은 각각 최신 25개이며
`findings_page`, `events_page`에 전체 건수·삽입 상한·추가 페이지 여부를 반환한다.
과거의 전체 발견 배열이나 최대 1,000개 이벤트를 기대하는 클라이언트는 전용 경로로
이동해야 한다. 이벤트 배열도 이전의 오름차순에서 최신 순서로 변경됐다.
작업 메타데이터·커버리지 구조와 `/messages` 경로는 유지한다.

콘솔 작업 모달은 두 목록을 독립적으로 검색·페이지 조회한다. 발견 제목을 누르면
해당 발견 상세로 이동한다. 목록은 4초마다, 작업 메타데이터는 2.5초마다 갱신하며
늦게 도착한 이전 요청은 화면에 적용하지 않는다. 모달을 닫으면 검색·페이지 상태는
초기화하며 열린 작업 ID의 URL 복원은 아래 계약을 따른다. snapshot은 새 삽입을 제외하는
상한이며 기존 행의 수정까지 고정하는 데이터베이스 스냅샷은 아니다.
MCP 이벤트 조회도 같은 SQL 페이지 구현을 사용한다.


## 작업 대화 이력

`GET /api/tasks/{task_id}/messages/page`는 기본 25개·최대 100개, offset·snapshot·
search(최대 200자)와 공통 페이지 응답을 사용한다. 내용·역할(user/assistant)을 문자
그대로 검색하고 해당 작업의 메시지만 최신 삽입 순서로 반환한다. 없는 작업은 404,
잘못된 경계는 422, 인증되지 않은 조회는 401이다. 조회 역할도 읽을 수 있으나 질문
POST는 관리자·운영자만 가능하다. messages를 공용 `/records/{kind}`에 공개하지 않는다.

기존 `/messages` GET의 배열 구조는 유지하지만 최신 1,000개까지만 반환한다.
선택한 배열은 오래된 삽입부터 반환하며 `X-Total-Count`, `X-Results-Limited`로
전체 건수·누락 여부를 알린다. 과거의 생성 시각 정렬 대신 삽입 순서를 사용하므로
가져온 기록의 created_at과 삽입 순서가 다르면 순서도 달라진다. 전체 이력 조회는
새 페이지 경로로 이동해야 한다.

대화 패널을 펼치면 검색·페이지 조회를 시작하고 접으면 주기 조회를 멈춘다.
페이지는 최신부터 선택하지만 페이지 내부 메시지는 오래된 순서로 표시한다.
질문 저장 후 검색·페이지를 초기화하고 새 답변을 보이도록 스크롤한다. 별도의 조회
오류가 저장된 질문을 다시 전송하지 않으며 실패한 POST에서는 질문 입력을 보존한다.
중복 클릭은 전송 중 잠금으로 방지한다. POST에 선택적 request_id(16–80자 ASCII
영문·숫자·밑줄·하이픈)를 보내면 인증 사용자·작업·전송 ID별로 한 쌍만 저장한다.
같은 ID와 질문의 재시도는 최초 답변의 ID·내용·시각을 그대로 반환하고, 다른 질문에
같은 ID를 쓰면 409다. 서로 다른 사용자·작업의 같은 토큰은 독립적이다. SQLite의
BEGIN IMMEDIATE와 기본키가 별도 Store 연결의 동시 재시도에도 중복을 막는다.
저장된 메시지가 유지되는 동안 서버 재시작 후에도 동일하게 동작하며, 별도 메모리
캐시나 만료 시간은 없다. 기존 request_id 없는 클라이언트는 매번 새 대화를 저장한다.

화면은 전송 전에 사용자·작업별 sessionStorage 항목에 질문과 전송 ID를 보관한다.
응답을 확인하기 전 상세를 닫거나 같은 탭에서 문서를 다시 열면 대화 패널을 펼치고
미확인 질문을 복원한다. 같은 내용으로 수동 재시도하면 원래 ID를 유지한다. 자동
전송은 하지 않는다. 성공 응답을 확인한 뒤 해당 ID의 보관 정보를 제거하고, 늦은
응답은 다른 ID의 새 정보를 지우지 않는다. 질문을 바꾸면 새 ID로 전송한다.

“미확인 전송 지우기”는 이 탭의 재시도 정보만 지우며 서버 대화는 삭제하지 않는다.
브라우저 저장소가 막히거나 가득 찼으면 안내와 함께 패널 메모리에서만 재시도할 수
있다. 성공 후 삭제 실패도 안내하며, 이미 저장된 정보의 삭제 실패를 성공으로
표시하지 않는다. 저장 데이터는 버전·내용 길이·ID 형식을 검사한다. 사용자 ID와
작업 ID별로 분리하며 다른 사용자로 로그인하면 해당 사용자의 질문만 복원한다.
내용은 브라우저 저장소의 평문으로 탭 수명 동안 남는다. 로그아웃 후 같은 탭에서
같은 사용자로 다시 로그인하면 복원 가능하다. 탭 종료·저장소 삭제·다른 기기나 탭의
독립 저장소 사이에서는 복구를 보장하지 않는다. 이 기능은 전송한 미확인 질문만
보존하며, 전송 전 입력은 보존하지 않는다. 대화 내부 검색·페이지·펼침은 아래
URL 계약으로 보존한다. 질문과 전송 ID는 URL에 넣지 않는다.

규칙 기반 답변은 해당 작업의 발견을 심각도 우선 SQL 조회로 최대 8개만 읽으며
관련 ID 배열은 요약한다. 질문·답변은 동일 트랜잭션에 저장하여 답변 쓰기가 실패하면
질문 쓰기도 롤백한다. 대상 HTTP 요청이나 명령은 실행하지 않는다. 내부 커버리지 조회의
전체 메모리 상한, AI 대화·실행 개입, 보존 정책은 별도 후속 작업이다.
보고서는 전체 목록을 모으지 않고 읽기 스냅샷에서 스트리밍한다([REPORTS.md](REPORTS.md)).

## 작업·발견 상세 URL

콘솔은 `detail=task|finding&detail_id=...`로 열린 기록을 보존한다. 기록 ID는
영문·숫자·밑줄·하이픈 1–80자만 허용하며 잘못된 상세 매개변수는 초기 탐색에서
제거한다. URL은 인증을 대신하지 않는다. 로그인 상태가 아니면 로그인 화면을
표시하고 인증 후 해당 상세를 다시 조회한다.

상세 열기·닫기·기록 간 이동은 브라우저 이력에 추가한다. 원래 page와 해당 목록의
검색·필터·offset·snapshot 및 그래프 매개변수는 유지한다. 일반 화면 이동은 상세를
닫으며, 새 문서·새 탭에서 유효한 상세 URL을 열면 같은 기록을 조회한다. 모달의
이전/다음 화면 버튼은 실제 브라우저 이력을 사용하여 배경이 비활성인 동안에도
탐색할 수 있게 한다. 닫기 뒤 이전 탐색은 방금 닫은 상세를 다시 연다.

로딩·초기 조회 오류는 상세 모달에서 구분하며 오류에는 다시 불러오기 버튼을 제공한다.
작업은 첫 조회가 성공한 뒤 2.5초마다 갱신한다. 초기 실패는 자동 반복 조회하지 않으며,
갱신 오류 때는 마지막 기록이라는 표시를 제공한다. 다른 상세로 이동하거나 닫은 뒤
도착한 이전 응답은 취소 신호와 현재 URL 확인으로 화면에 적용하지 않는다.

발견의 증거·재검증 목록은 아래 계약으로 펼침·검색·페이지 위치도 보존한다.
변경 이력도 아래 계약으로 펼침·검색·페이지를 보존한다. 개별 증거 원본의 펼침·스크롤 및
미저장 조치 입력은 URL에 보존하지 않는다.
자산 편집·트래픽 상세 등 나머지 모달과 전체 모바일/접근성 회귀도 후속 작업이다.


## 자산 변경의 선택적 조회

자산 등록·가져오기·주소 변경의 중복 검사는 URL 존재 여부만 SQL에서 확인하며,
보관된 자산의 주소도 예약된 것으로 취급한다. URL 표현식 partial index는 Store를
열 때 멱등적으로 생성한다. 첫 생성 시 기존 자산의 인덱스 작성 시간·디스크 공간은
필요하다. 실행 중 여부와 주소 변경을 막는 이력 존재 여부는 작업의 asset_ids 배열을
SQLite json_each로 검사한다. 전체 작업 payload를 Python에 모으지 않지만 배열
관계가 정규화된 전용 참조 테이블은 아니므로 조회 CPU 시간은 전체 기록에 영향받는다.

보관 시 중지할 예약은 활성 예약 중 해당 자산을 참조하는 ID만 읽는다. 읽기 cursor의
스냅샷 동안 별도 WAL 연결에서 중지 상태를 저장하며, 다른 자산의 예약과 이미 멈춘
예약은 건드리지 않는다. 복원은 예약을 자동 재개하지 않는다. 감사 이벤트에 남기는
중지 예약 ID 목록은 기존대로 전부 유지하므로 해당 연결 수에 비례한 ID 메모리와
감사 payload 크기는 아직 남는다. 자산 변경의 기존 잠금·revision·역할 검사도 유지한다.


## 발견 증거·재검증·변경 이력의 상세 북마크

유효한 finding 상세에서 다음 세 접두사를 독립적으로 사용한다.

| 목록 | URL 접두사 | 필드 |
| --- | --- | --- |
| 증거 이력 | `finding_evidence_` | `open`, `q`, `offset`, `snapshot` |
| 재검증 이력 | `finding_retests_` | `open`, `q`, `offset`, `snapshot` |
| 변경 이력 | `finding_history_` | `open`, `q`, `offset`, `snapshot` |

open=true이면 펼친다. 검색은 200 UTF-16 코드 단위 안에서 서로게이트를 끊지 않고
제한한다. offset은 0–10,000,000의 25개 페이지 경계로 보정하고 snapshot은 음수 없는
안전 정수만 허용한다. 잘못된 값·기본값은 초기 URL 정규화에서 제거한다. 검색 변경은
해당 목록의 첫 페이지·새 조회로 돌아가며 다른 목록과 배경 목록 조건은 유지한다.
검색 입력은 현재 이력을 교체하고 펼침·페이지 이동은 이력에 추가한다. 최신 목록은
해당 목록의 offset과 snapshot을 초기화한다.

목록을 접으면 조회를 멈추되 검색·위치를 유지한다. 새 문서나 복사 URL은 세 목록의
펼침·검색·삽입 상한·페이지를 복원하고, 상세의 이전/다음 버튼으로 같은 조건을
되돌릴 수 있다. 같은 발견을 유지한 URL 정규화는 이 조건을 보존한다. 다른 발견이나
작업으로 이동하거나 상세를 닫으면 세 접두사의 필드를 지워 조건이 다른 기록에
이어지지 않게 한다. 현재 발견 ID와 목록 상태를 확인한 뒤에만 비동기 페이지 보정을
URL에 반영한다. 원본 증거의 개별 details 펼침·스크롤·미저장 조치는 별도 상태다.

## 작업 상세 목록의 URL 상태

`detail=task&detail_id=<id>`일 때 발견 목록은 `task_findings_q/offset/snapshot`,
실행 기록은 `task_events_q/offset/snapshot`을 사용한다. 두 목록의 검색과 페이지는
독립적이며 새 문서에서 복원된다. 검색 입력은 현재 history entry를 replace하여
매 글자마다 이력을 만들지 않고, 해당 목록의 offset·snapshot을 초기화한다.
페이지 이동은 push, 응답에 따른 위치 보정은 replace다. 삽입 상한은 페이지 이동에
사용하며 첫 페이지의 기본 null은 최신 조회를 허용한다.

같은 작업의 정규화는 상태를 유지한다. 다른 작업/발견을 열거나 상세를 닫으면 작업
접두사 필드를 지운다. 이전 탐색으로 원래 작업 URL에 돌아오면 그 entry의 검색과
페이지가 다시 복원된다. 원본 작업 목록의 검색·필터·페이지는 함께 유지한다.
검색은 최대 200자, offset은 25단위로 정규화하며 snapshot은 안전한 정수만 허용한다.
현재 작업 ID와 해당 목록 상태가 여전히 같은 경우에만 비동기 페이지 보정을 적용한다.
대화는 아래 계약을 따른다. 개별 기록 details 펼침과 스크롤은 아직
이 URL 계약에 포함되지 않는다.

## 작업 대화의 URL 상태

`detail=task&detail_id=<id>`에서 `task_chat_open=true`로 대화를 펼친다.
`task_chat_q`, `task_chat_offset`, `task_chat_snapshot`으로 검색·페이지·삽입 상한을
복원한다. 검색은 최대 200자이며 surrogate pair를 자르지 않는다. offset은
0–10,000,000의 25단위, snapshot은 JavaScript 안전 정수만 허용한다. 초기 탐색과
변경 시 잘못된 값을 정규화한다. URL은 메시지나 계정의 조회 권한을 부여하지 않는다.

검색 변경은 현재 이력을 교체하고 대화의 offset·snapshot만 초기화한다. 펼침·접기와
페이지 이동은 이력을 추가한다. 접기는 대화의 검색·페이지를 유지하고 주기 조회를
멈춘다. 다른 작업·발견으로 이동하거나 상세를 닫으면 대화 매개변수를 지운다.
닫기 후 이전 탐색이나 새 문서의 북마크로 같은 상태를 다시 열 수 있다. 작업의
발견·실행 기록과 배경 목록의 검색·페이지는 별도로 유지한다.

조회 응답의 위치 보정은 작업 ID와 현재 대화 URL 상태가 일치할 때만 반영한다.
전송 당시의 화면을 유지한 질문 저장 성공은 대화를 펼치고 검색을 지우며 최신
페이지·새 답변으로 이동한다. 응답 대기 중 검색·페이지·펼침 또는 상세 화면을
바꾸면 늦은 성공은 현재 탐색을 유지하고 전역 저장 안내를 표시한다. 다른 목록의
스냅샷을 초기화하지 않으며, 현재 대화는 기존 기준점으로 주기 조회한다.
저장 오류에서는 질문과 대화 위치를 유지하며, 이전 화면의 늦은 오류는 현재
화면의 오류로 표시하지 않는다. 상세를 닫은 뒤 성공을 확인해도 해당 전송 ID의
재시도 정보를 정리하며, 더 새로운 전송 ID는 지우지 않는다. 이미 다시 열린
패널의 복원 상태는 자동 동기화하지 않으므로 같은 ID로 재시도해 확인할 수 있다.
같은 탭의 미확인 전송이 복원되면
패널을 펼치되 기존 검색·페이지는 유지한다. 수동 재시도는 기존 전송 ID를 사용한다.
전송 전 초안·메시지 내부 스크롤은 복원하지 않는다. 검색어는 URL에 남으므로
인증정보나 민감 원문을 검색어로 사용하지 않는다.
