# 결과에 따른 다음 계획

`GET /api/tasks/{id}/next-plan`은 승인 후 종료된 작업의 커버리지에서 다음 검증을
제안한다. 조회와 제안 반영은 대상 요청을 보내지 않는다. 현재 규칙 기반 제안이며
LLM의 자유로운 목표 분해·관찰 URL 실행·이벤트마다 자동 계획하는 기능은 남아 있다.

원본과 연결된 과거 회차의 자산별 최신 결과를 한 읽기 스냅샷으로 읽는다.
실패·취소·중단·누락·오래된 결과는 재검증 후보로, 아직 선택하지 않았던 내장 검증은
추가 후보로 제안한다. 동일 revision과 현재 도구 계약의 완료 결과는 다시 제안하지 않는다.
도구 계약이 없거나 현재 패키지/버전과 다르면 과거 결과를 오래된 결과로 처리한다.
건너뜀은 성공으로 해석하지 않으며 제안 근거에 별도로 남긴다. 반복 계획에서 이미
선택한 검증을 매번 미선택으로 오인하지 않도록 이전 회차도 확인한다.

현재 작업 구조는 모든 선택한 자산에 같은 도구 목록을 적용한다. 따라서 어느 자산의
실패 때문에 도구를 다시 선택하면 다른 자산의 완료 검증도 반복될 수 있다.
`repeated_completed_cells`에 이를 표시한다. 원본 자산 ID와 Worker 의존 관계는
그대로 보존하며, 관찰된 URL을 새 자산으로 추가하지 않는다. 현재 자산의 이름·주소·
revision, 도구 계약과 실행 정책은 새 승인 계획에 반영한다.

`POST /api/tasks/{id}/next-plan`에 조회한 `fingerprint`를 제출하면 운영자/관리자가
새 `pending` 계획을 만든다. 원본의 `next_plan_id`와 새 계획의 `followup_of`,
`followup_fingerprint`, `planning_round`를 커버리지와 같은 트랜잭션으로 저장한다.
동시 클릭과 재시도는 같은 계획을 반환하며, 이미 종료된 새 계획도 중복 생성하지
않는다. 실제 실행에는 기존 관리자 승인이 필요하다. 결과·자산·정책 등이 바뀐
제안은409이며 다시 조회해야 한다. 지문은 저장 메타데이터 변경 검사이며 서명이나
DB 관리자에 대한 변조 방지 보장이 아니다.

처음 작업은0회차이며 후속 계획은 최대8회차다. 같은 원본에서 다음 계획을 하나만
만든다. 회차·원본/후속 연결·자산 ID가 맞지 않거나 연결이 순환하면 제안을 거절한다.
모든 내장 검증에 최신 완료 또는 건너뜀 결과가 있고 재시도 후보가 없으면 제안이
없다. 이것은 해당 자산이 안전하다는 판정이 아니다. 실패의 원인을 수정하지 않은
채 반복 승인하면 같은 요청이 반복될 수 있다.

현재 HTTP 계약을 구현했으며 전용 제안 검토 UI, 사람의 계획 수정/대화 개입,
공유 할 일과 자동 이벤트 기반 Planner는 후속 작업이다. 실제 외부 LLM 또는
운영 대상 서버에서 검증한 기능이라고 주장하지 않는다.
