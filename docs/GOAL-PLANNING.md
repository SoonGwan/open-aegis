# 목표를 검토 가능한 검증 과제로 분해

일반 대기 계획 또는 종료 작업의 상세에서 검증 목표와 초안 방식을 선택한다.
**AI**는 설정된 제공자가 자연어 목표를 과제로 분해한다. **규칙**은 등록된
6개 도구의 검토 목록이며 자연어 의미 이해를 수행하지 않는다. AI 응답을
확인하지 못하면 규칙 복구임을 표시하고 호출 결과/사용량을 남긴다.

초안 생성은 대상 요청이나 승인 대기 작업 생성이 아니다. 운영자가 초안의
과제·선택 자산·도구·기대 근거·필요한 입력·Worker 의존 관계를 검토한 후 반영하면
별도의 승인 대기 작업이 생긴다. 기존 작업은 유지되며 관리자의 새 실행 승인이
필요하다. 승인 후에는 기존 Worker/도구/범위/실행 예산으로 실제 검사한다.

## 입력과 응답 계약

관리자·운영자의 `POST /api/tasks/{source_id}/goal-plans`는 goal(최대2000자),
mode(rules/ai), request_id(32자리 소문자16진수)를 받는다. source+request_id의
결정적 키로 생성 중/준비/중단 상태를 저장한다. 동일 요청의 재시도는 기존
레코드를 돌려주며 응답 유실이나 중단으로 결과가 미확인인 경우에도 제공자를
자동 재호출하지 않는다. 같은 ID로 다른 입력은409다. 새 호출은 새 요청이어야 한다.

`GET /api/tasks/{source_id}/goal-plans/{draft_id}`는 조회 권한으로 읽는다.
`POST .../{draft_id}/accept`의 fingerprint는 검토한 초안과 일치해야 한다.
이미 반영한 초안은 같은 기존 작업을 반환한다. 반영은 출처 상태·목표·현재 자산·
권한 규칙 지문·도구 계약·실행 정책·공유 할 일/관찰 맥락을 최종 쓰기 트랜잭션에서
다시 확인한다. 변경·손상된 초안은 거절하고 작업/커버리지/초안 연결을 일부 남기지 않는다.

AI에는 운영자가 입력한 목표, 자산 ID/이름/유형/권한 규칙 개수, 활성 공유 할 일과
검증된 관찰의5개 필드만 보낸다. 자산 URL·권한 규칙 경로/내용·응답 원문·환경변수
인증 값은 자동 전송하지 않는다. 운영자 입력에 직접 쓴 내용은 입력으로 전송된다.
기존 제공자 TLS/주소/리다이렉트/출력/시간 제한과 종료 중단 제어를 사용한다.

응답의 정확한 최상위 필드는 objectives와 worker_dependencies다. 최대12개 과제,
32KiB JSON에 다음 필드만 허용한다.

- id: g1부터g12 사이의 중복 없는 식별자.
- title: 최대200자; rationale/expected_evidence: 각각 최대1000자.
- asset_ids: 출처에 포함된 현재 활성 자산 중1–20개, 중복 금지.
- checks: 등록된6개 도구 중1–6개, 중복 금지.
- missing_inputs: 최대8개 문자열, 각400자 이하.

의존 관계는 선택한 자산의 비순환 DAG이며 기존20개 자산/40개 연결 제한을 따른다.
임의 URL·명령·외부 도구 필드를 실행 입력으로 받지 않는다. 과제 설명/기대 근거는
신뢰할 수 없는 검토 텍스트이며 사실성을 독립 검증한 것으로 표시하지 않는다.
제공자 키를 포함한 응답과 계약을 벗어난 응답은 저장하지 않고 규칙으로 복구한다.

## 실행 연결과 진행률

선택 자산은 과제 asset_ids의 합집합, 선택 도구는 과제 checks의 합집합이다.
새 초안에는 지문에 포함되는 execution=objective_pairs를 고정하며, Worker는
**각 과제에 선언된 자산 × 도구 조합의 합집합**만 검사한다. 여러 과제가 같은 조합을
요청하면 한 번 실행하고 결과를 공유한다. 과제에 없는 자산/도구 조합의 커버리지는
생성하지 않으며 새 작업이 그 조합의 이전 증거를 덮어쓰지 않는다.

execution 필드가 없는 기존 초안/작업은 승인 당시 **선택 자산 × 선택 도구의 전체
조합** 계약을 유지한다. 화면은 기존/새 계약을 구분하며 교체·재실행도 같은 계약을
유지한다. 필드를 제거하거나 바꾸면 저장 지문과 일치하지 않아 승인을 거절한다.
새 승인에 선택 도구와 모든 자산 범위를 보여준다. Worker 의존 관계는 실제
실행에 적용하며 선행 자산에 지정된 검사가 모두 완료되지 않으면 후행 요청을
보내지 않는다. 전달하는 완료 도구 목록도 선행 자산의 실제 선택 목록이다.

작업에 고정한 goal_plan의 목표·과제·도구·자산·의존 관계·지문은 승인/실행 전에
검사한다. 교체/재실행은 같은 과제를 유지하며 현재 범위를 새로 승인한다.
설명은 새 모델 추론 결과가 아니므로 수정된 목표에는 새 초안을 준비해야 한다.

`GET /api/tasks/{task_id}/goal-progress`는 과제별 자산/도구의 실제 커버리지를
집계한다. 누락/실패/건너뜀은 완료가 아니며 범위가 없는0/0 결과를 완료로
표시하지 않는다. expected는 과제에 선언된 자산 수 × 도구 수다. goal_verified는
항상false이며 검사 완료만으로 자연어 목표나 기대 근거가 충족됐다고 판정하지 않는다.

## 과제별 발견·재검증 연결

`GET /api/tasks/{task_id}/goal-objectives/{objective_id}/findings`는 조회 권한으로
과제에 해당하는 발견을 검색·페이지 조회한다. limit1–100(기본25), offset0–10000000,
snapshot0–9223372036854775807, 제목 search 최대200자를 받는다. SQL에서 제한된
요약만 읽으며 SQLite/PostgreSQL 모두 한 읽기 트랜잭션의 결과를 반환한다.

발견의 작업 참조에 출처 작업이 있고, 발견이 참조한 실제 evidence 레코드의
작업·자산·검사·지문이 출처 과제와 일치해야 연결한다. task_ids만 붙인 발견이나
다른 작업의 증거는 포함하지 않는다. 원문 증거/전체 관련 ID 배열을 응답하지 않고
일치한 증거 개수와 발견 요약을 제공한다. snapshot은 발견의 rowid 삽입 상한이며
이미 있던 발견의 조치 상태/증거/재검증 변경을 동결하지는 않는다.

재검증 개수와 최근 결과는 해당 발견을 retest_of로 가리키는 승인 작업과 연결된
retests 레코드 중, 같은 단일 자산/검사와 저장 범위의 자산 ID가 일치하고 결과가
resolved/reproduced/inconclusive인 이력이다. 손상된 참조/범위/미승인 이력은 제외한다.
원래 목표의 범위 revision과 같은 검사라고 주장하지 않는다. 발견 상세나 최근
재검증 작업을 열어 당시 범위·조치 충돌·증거를 확인해야 한다.

과제별 진행률을 조회한 뒤 ‘근거·재검증 확인’에서 검색·페이지를 열고 발견 상세의
기존 재검증 생성/승인 흐름으로 이동한다. 새 검사나 제공자 호출 없이 조회한다.
같은 발견의 재검증 이력은 다른 작업에서 만든 이력도 포함하며, 목표에서 생성한
전용 후속 회차라고 표시하지 않는다. 재검증 결과는 원래 작업의 완료율을 바꾸거나
자연어 목표 달성을 판정하지 않는다. 진행률 열기와 과제별 발견의 적용한 검색어·
페이지·증거 스냅샷은 작업 상세 URL에 저장한다. 새 문서에서도 저장된 과제 목록을
조회하고, 발견/재검증 상세에서 뒤로 이동하면 같은 위치를 복원한다. 입력 중인
미적용 검색어는 저장하지 않는다. 각 과제의 검색과 위치는 독립적이다.

URL 과제 ID는 g1..g12만 허용하며 실제 작업의 과제 목록에 있는 항목만 조회한다.
검색어는 최대200자, 페이지 위치는25개 단위와10,000,000 이하, 스냅샷은 안전한
정수로 정규화한다. 다른 작업/발견/메뉴 이동이나 상세 닫기는 목표 조회 상태를
제거한다. 이전 응답의 위치 보정은 작업·과제·검색·페이지·스냅샷이 여전히 같은
경우에만 저장한다. 조회 실패는 빈 결과와 구분하며 재시도는 저장된 위치를 유지한다.
`최신 목록`은 검색어를 유지하며 첫 페이지와 새 스냅샷으로 이동한다. URL에는 검색어가
포함되므로 공유할 주소의 내용을 확인한다. 주소 복원은 조회이며 실행 승인이 아니다.

원본 작업의 실행 승인 시각은 양수의 유한 숫자여야 한다. 기록이 없거나 bool·문자열·
0·음수이면 발견/증거가 연결돼 있어도 과제 근거로 표시하지 않고, 기록된 완료 상태는
과제 진행률에서 not_recorded로 취급한다. 정상 미실행 not_started 상태는 유지한다.
해당 원본의 새 과제 재검증과 후속 제안도 거절한다. 기존 증거는 삭제하지 않는다.
관련 재검증 결과도 같은 승인 시각 형식이 있어야 이력/최근 결과에 포함한다.
이는 로컬 저장 계약의 일관성 검사이며 숫자 시각만으로 외부 출처를 인증하지 않는다.

## 목표의 후속 회차

승인되어 종료된 목표 작업의 결과 기반 다음 계획은 같은 goal_plan을 유지한다.
미실행 카탈로그 도구를 자동으로 추가하지 않는다. 실패/중지/누락/오래된 선택 검사나
범위 안의 활성 공유 할 일 요청이 있으면 원래 과제의 **전체 선택 조합**을 새 회차로
제안한다. 자산별 선택 조합·Worker 의존 관계는 유지하며, 완료된 검사도 다시 실행한다.
실패한 셀만 실행하는 최적화는 현재 지원하지 않는다. 반복되는 완료 셀을 검토 화면에
표시하고 현재 자산/정책/도구의 새 승인 후 실행한다. 새로운 AI 추론을 수행하지 않는다.

목표 밖의 공유 할 일 검사 요청은 goal_scope_change_required로 반영을 거절한다.
새 목표 초안을 검토해 범위를 변경해야 하며, 해당 요청을 조용히 추가하거나 무시한
후속 계획을 만들지 않는다. 선택 검사가 끝나고 요청이 없으면
no_remaining_goal_checks다. 이것은 목표 달성이나 발견 해결 판정이 아니다.

원래 goal_plan이 제안 지문에 포함되며 최종 반영에서 현재 근거를 다시 확인한다.
후속 작업과 교체/재실행은 같은 과제/초안 참조를 유지한다. 후속의 새로운 실행 증거는
해당 회차의 과제별 발견과 진행률에서 확인한다. 기존8회차·32개 이력 제한과
중복 생성/현재 계획 이동을 사용한다. 이전 버전에서 과제 참조 없이 만들어진
후속 이력이 섞인 목표는 새 초안 검토를 요구한다. 목표 발견 재검증은 이 경로에서
도구를 추가하지 않고 원래 과제의 재검증 생성 흐름을 사용한다.

## 목표에서 만드는 재검증 계획

운영자는 `POST /api/tasks/{source_id}/goal-objectives/{objective_id}/findings/{finding_id}/retest`
에 request_id(32자리 소문자16진수)만 보낸다. 조회자는 생성할 수 없다.
같은 출처·과제·발견·요청 ID는 결정적 작업 키로 같은 원본 작업을 돌려준다.
그 작업이 교체/종료돼도 원래 요청의 결과를 반환하며 이력에서 현재 계획을 확인한다.
같은 발견의 다른 활성 재검증이 있으면 과제 참조를 덧붙이거나 바꾸지 않고409로 거절한다.

생성 시 실제 과제의 원본 증거 연결을 확인하고 최종 쓰기 트랜잭션에서 출처 계획 지문과
발견 연결·현재 자산을 재검사한다. task/coverage/감사 기록을 원자 저장한다.
원래 과제 전체를 재실행하지 않고 해당 발견의 단일 자산/검사 재검증을 만들며
기존 요청 제한·현재 범위의 별도 관리자 승인을 따른다. 제공자를 호출하지 않는다.

작업의 goal_retest는 원래 작업/과제/발견 식별자와 이름, 원래 계획/발견 지문,
단일 자산/검사·요청 ID와 일관성 지문을 고정한다. 승인·실행 전에 이 참조와
실행 자산/검사/발견/저장 범위가 일치하는지 검사한다. 이는 저장 계약의 일관성 검사이며
원래 목표의 의미적 달성이나 외부 서명 검증이 아니다. 교체·재실행은 같은 참조를
유지하며 결과의 retests 레코드에도 복사한다. 참조는 역사적 출처이며 원래 목표를
나중에 변경/삭제한 경우까지 현재 의미가 동일하다고 보장하지 않는다.

과제별 발견에서 ‘이 과제의 재검증 계획 만들기’를 누르면 사용자/출처/과제/발견별
같은 탭 저장소에 요청 ID를 POST 전에 저장한다. 응답 유실이나 새로고침 후 원래
목표의 진행률과 근거를 다시 열면 같은 요청을 확인할 수 있다. 저장소를 사용할 수
없으면 POST하지 않는다. 생성 결과는 승인 대기이며 상세에서 원래 목표/발견으로
이동할 수 있다. 원래 목표의 검사 완료율은 재검증 결과로 바꾸지 않는다.

## 내구성·사용량·화면

제공자 호출 시도는 기존 독립 llm_calls에 planner 종류로 기록하고 phase를
goal_decomposition으로 남긴다. 응답 관찰 뒤 초안/호출 확정/감사 이벤트를 함께
저장한다. 저장 실패는 미확정 호출을 남기고, 재시작은 생성 중 초안을 중단 상태로
복구한다. 재시작이 새 유료 호출을 발생시키지 않는다.

계획 사용량에는 작업의 최신 순서 계획과 저장된 목표 초안 호출을 함께 집계한다.
SQLite/PostgreSQL 모두 같은 메타데이터만 집계하며 제공자 보고·누락·부분·잘못된
사용량과 실제 청구를 구분한다. usage API의 설명용 scope는
latest_task_planner_and_persisted_goal_draft_calls와
latest_task_planner_goal_draft_and_persisted_conversation_calls로 확장했다.

화면은 AI 전송/비용을 설명하고 요청 입력·ID를 POST 전에 사용자/출처별 같은 탭
저장소에 저장한다. 새 문서에서 같은 요청으로 초안을 확인할 수 있다. 저장소를
사용할 수 없으면 생성 요청을 보내지 않는다. 저장된 요청의 결과가 확정된 뒤
새 초안을 준비한다. 실제 검사 진행률과 검토용 기대 근거를 별도로 보여준다.

## 설치 패키지의 백업·복구 검증

`scripts/review_goal_recovery.py --wheel <wheel> --backend both`는 저장소 밖의 새
설치와 소유한 loopback HTTP 대상으로 SQLite/PostgreSQL을 각각 검증한다.
실제 규칙 목표의 증거를 기록하고 후속/과제 재검증의 교체 계획을 승인 대기로
저장한 뒤 서버를 정상 종료한다. 설치된 CLI의 백업·검사·복구·감사 체크포인트
비교 후 이전 세션을 거절하며 원래 요청 ID와 현재 교체 계획을 보존한다.

복구한 계획은 새 승인 전 대상 요청을 보내지 않는다. 각각 명시적으로 승인한 뒤
실제 HTTP 재검증의 해결 결과와 과제 출처·후속 회차를 확인하고, 복구본 서버를
다시 열어 결과와 중복 요청의 식별을 확인한다. 원본 감사 로그는 유지되고 복구본
감사 체인은 원래 체크포인트를 이어간다. 규칙 목표에는 등록 도구 전체가 포함되며
API 규칙 없는 권한 검사는 건너뜀이다. 검사 완료나 복구 성공은 의미적 목표 달성
판정이 아니다. 이 검증은 정상 종료 후 백업이며 전원 장애·PITR·원격 백업이나
상용 AI 제공자 검증을 대신하지 않는다.

`--crash`를 추가하면 소유한 서비스 프로세스를 SIGKILL로 종료한다. 승인 대기
계획 저장 후 재시작에서 요청 식별과 미실행 상태를 검증하고, 실제 GET 요청이
들어온 재검증/후속 작업을 각각 중단한다. 재시작은 원래 과제 참조를 가진
`interrupted` 결과로 복구하며 자동 재실행하지 않는다. 각 중단 작업에 같은 재시도
요청을 반복해도 승인 대기 작업은 하나만 생성되고 새 승인 뒤 완료한다. 마지막
재시작에서 과제 출처·해결 결과·현재 회차 연결과 감사 체인도 확인한다. 이 모드는
DB와 호스트가 계속 실행되는 프로세스 종료이며 전원 장애나 DB 서버 중단의 근거는 아니다.

PostgreSQL에서는 `--backend postgres --crash --database-crash`로 소유한 임시 DB
클러스터도 `pg_ctl -m immediate`로 중단할 수 있다. 승인 대기 계획 저장 뒤
서비스가 종료된 상태에서 DB를 중단·재시작하고, 시작 로그의 WAL 복구와 중단
전후 동일한 감사 체크포인트를 확인한다. 이어 요청 식별·계획·미실행 상태 보존과
명시적 재승인 후 실행까지 검증한다. `--backend both`도 지원하며 SQLite에는 DB
중단을 적용하지 않는다. 호스트·저장 장치는 살아 있으므로 하드웨어 전원 장애,
저장 장치 장애, PITR 검증은 별도다.

여기에 `--database-crash-in-flight`를 추가하면 새 승인으로 보낸 재검증/후속
재시도 GET의 응답을 보류한 상태에서도 DB를 각각 중단한다. 살아 있는 서비스는
실행 소유권을 잃어 조회·승인·health를503으로 거절하며 자동 재연결·재승인하지
않는다. 소유한 서비스를 종료·재시작하면 해당 작업은 출처와 회차를 유지한
`interrupted`로 복구한다. 중복 요청에도 승인 대기 재시도 하나만 만들고, 새 승인
후 완료와 최종 재시작의 결과·감사 연결을 확인한다. PostgreSQL에는 대상 GET7회,
서비스 SIGKILL5회, DB immediate 중단3회를 적용한다. SQLite에는 기존 서비스
중단 검증만 적용한다. HTTP 응답 대기 중의 장애 검증이며 DB 쓰기 트랜잭션 도중
장애, 전원·저장 장치 장애, PITR은 별도다.

## 남은 검증과 확장

상용 제공자의 실제 목표 분해 품질/호환성 평가는 미실행이며 현재 근거는 모의
제공자 계약과 소유한 HTTP 대상의 승인 실행이다. 기대 근거의 의미적 충족 판정, 실패 셀만의 후속 실행 최적화,
관찰 URL 선택과 통합된 목표 분해, 초안 목록/검색/보존 정책, 전체 역할/탐색 경합과
모바일/스크린리더 여정은 남아 있다. 이 단계만으로 전체 Planner v1을 완료하지 않는다.
