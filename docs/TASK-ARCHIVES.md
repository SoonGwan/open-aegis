# 종료 작업 보관·복원

보관은 종료 작업을 일반 목록과 보관함 사이에서 정리하는 변경이다. 실행 상태,
승인·범위·계획·Worker 결과와 증거를 변경하지 않는다. 완료·실패·중지·서버 중단·
승인 거절 작업만 보관·복원하며 대기·실행 중인 작업은 전체 요청을 거절한다.
운영자와 관리자가 변경하고 열람자는 읽기만 가능하다. 저장 직전 DB의 현재 역할을
다시 확인한다.

한 번에1–25개의 작업 ID와 선택 당시 보관 변경 버전을 제출한다. 버전은 최초0이며
실제 보관 상태가 바뀔 때 증가한다. 하나라도 없거나 버전·상태가 맞지 않으면 모든
작업을 유지한다. 변경된 작업·각 보관 이력·요청 영수증·감사를 같은 트랜잭션에
저장한다. 이미 같은 보관 상태인 작업은 버전과 이력을 추가하지 않는다.

같은 수행자·요청 ID·입력을 재시도하면 처음 영수증을 반환한다. 이후 다른 사람이
복원했어도 원래 보관 요청의 재시도가 다시 보관하지 않는다. 작업 순서만 바뀐
요청은 같은 입력이다. 요청 ID는16–80자이며 같은 ID로 다른 입력을 보내면409다.

화면은 선택 당시 작업/버전을 고정하고 최대25개를 선택한다. 주기적 조회가 최신
버전을 자동 채택하지 않는다. 응답 손실 뒤 같은 ID로 다시 저장한다. 충돌 시 창을
닫고 선택을 해제한 뒤 현재 작업을 다시 선택한다. 페이지·검색·상태·보관함 또는
사용자가 바뀌면 선택을 해제한다. 미확인 저장의 새 문서 복원은 제공하지 않는다.

일반 작업 화면은 `archived=false`, 보관함은 `archived=true`를 SQL 조회에 사용하며
검색·종료 상태·건수·페이지를 함께 적용한다. `tasks_archived=true`는 목록 위치와
함께 URL에 남는다. API에서 보관 필터를 생략하면 이전처럼 모든 작업을 조회한다.
자산 보관 필터와 작업 보관 필터는 서로 독립적이다. 상세의 보관 이력은25개 페이지다.

보관된 작업도 상세/증거/보고서를 읽을 수 있다. 대시보드·커버리지·관련 분류 집계는
전체 검증 이력을 계속 반영한다. 보관된 원본의 새 계획은 기존 규칙대로 별도의 새
승인을 요구한다. 복원이 과거 승인을 재실행하지 않는다.

- `POST /api/tasks/archive-assignment`: `task_ids`, `expected_revisions`, `archived`, `request_id`
- `GET /api/tasks/{id}/archive-history`
- `GET /api/records/tasks?archived=true|false`

현재 구현은 DB 안의 논리적 보관이다. 작업 삭제, 자동 보관, 압축 패키지 내보내기·
가져오기, 외부 객체 저장소, 전체 모바일/보조 기술, 설치본/구버전/백업 복구 검수는
후속 범위다. 전체 DB 백업·복구는 기존 관리 도구를 따른다.
