# 감사 로그 무결성

스키마 2는 events 원본과 별도의 event_hashes·audit_state를 사용한다. 기존 이벤트
조회 API의 형식은 유지한다. 새 이벤트·이전 해시·자체 해시·마지막 기준은 동일
SQLite BEGIN IMMEDIATE 또는 PostgreSQL의 직렬화된 쓰기 트랜잭션에 저장한다. 별도 Store 연결의 동시 기록도 순서를 공유하고,
해시 저장이 실패하면 이벤트 저장도 롤백한다.

업무 데이터 변경과 감사 이벤트는 별도 트랜잭션인 경로가 있다. 감사 기록이 실패해도
앞서 저장된 업무 변경이 자동으로 취소되지는 않는다. 이 연결은 모든 업무 변경의
기록 누락 방지나 업무 데이터 전체의 무결성을 보장하지 않는다.

SHA-256 입력은 UTF-8 JSON 배열 `[previous_hash, seq, ts, task_id, level, message,
detail]`이다. JSON 구분자는 쉼표와 콜론, ensure_ascii=False, 비유한 숫자는 거절한다.
SQLite에서 읽은 실제 ts 값과 detail 문자열 원본을 사용하므로 detail의 공백 변경도
검출 대상이다. 초기 previous_hash는 64개의 0이다. hash는 서명·암호화가 아니며
작업이나 기록 내용이 사실인지, 올바른 사용자가 변경했는지 증명하지 않는다.

버전 0·1 이벤트는 업그레이드 트랜잭션에서 삽입 순서대로 처음 봉인한다.
sealed_legacy_until은 그 마지막 seq다. 이 기준 이전 기록이 변조되지 않았다는
증거는 없다. 완료된 스키마를 다시 열 때 재봉인하지 않으며 불일치를 자동 수리하지
않는다. 이벤트를 기록할 때 기준 형식·마지막 seq/head와 마지막 이벤트의 실제 해시를
확인한다. 마지막 연결은 바로 앞 이벤트의 저장된 해시와도 비교한다. 전체 과거
연결은 매번 다시 읽지 않는다. 정기 검증으로 중간 기록의 불일치도 확인해야 한다.

seq는 양의 정수이며 과거 기록의 번호 사이에 빈 구간은 허용한다. 시각은 유한한
숫자, 나머지 이벤트 필드는 문자열 또는 NULL이어야 한다. 손상된 형식은 봉인·검증·
새 기록 저장에서 거절하며 오류에 기록 내용은 포함하지 않는다. chain_id는 32자리,
해시는 64자리 소문자 16진수다. sealed_legacy_until은 0 또는 존재하는 이벤트 번호이며
마지막 번호보다 클 수 없다. 이 검사만으로 유효한 범위 안에서 봉인 기준을 바꾼
것까지 인증하지는 않는다. 초기 봉인 기준도 별도 운영 기록으로 보존해야 한다.

## 검증과 체크포인트

```sh
.venv/bin/python scripts/verify_audit.py --source data/aegis.db
.venv/bin/python scripts/verify_audit.py --source data/aegis.db --output audit-checkpoints/first.json
.venv/bin/python scripts/verify_audit.py --source data/aegis.db --checkpoint audit-checkpoints/first.json
```

출력 디렉터리는 먼저 만든다. source는 읽기 전용 SQLite 연결이며 스키마를 수정하거나
업그레이드하지 않는다. 단일 읽기 스냅샷에서 순서대로 원본과 연결을 확인한다.
중간/끝 이벤트 삭제, 내용 변경, 누락 해시, 원본 없는 해시, 해시 없는 삽입, 기준
불일치가 있으면 실패한다. 일반 실패 종료 코드는 2다. 손상된 이벤트 내용은 오류에
출력하지 않으며 실패한 seq만 제공한다. 기록 전체를 Python 목록으로 모으지 않지만
가장 큰 단일 이벤트, SQLite 자원과 총 검증 시간에는 별도 강제 상한이 없다.

체크포인트는 format·chain_id·seq·hash만 포함한다. 이전 체크포인트는 현재 마지막
기록과 같을 필요가 없으며, 검증된 연결 안에 그 seq/hash가 그대로 있어야 한다.
다른 로그 ID, 변경된 이전 해시, 체크포인트보다 짧아진 로그는 실패한다.
output은 0600의 새 파일로만 생성하며 기존 파일을 덮어쓰지 않는다. 출력 전에
전체 연결을 확인한다. 파일 flush/fsync를 수행하지만 파일을 받는 쪽의 보관 신뢰·
원격 전달·서명·디렉터리 durability는 이 명령이 제공하지 않는다.

패키지 설치 환경의 `aegis-verify-audit`도 같은 옵션과 구현을 사용한다.
컨테이너 명령은 [OPERATIONS.md](OPERATIONS.md)에 정리했다.

## 신뢰 한계와 운영

DB에 쓰기 권한이 있는 공격자는 모든 이벤트와 해시·기준을 함께 다시 계산할 수 있다.
로컬 연결 검증만으로는 그 재작성을 구별하지 못한다. 공격자가 고칠 수 없는 독립
저장소의 체크포인트와 비교하면 해당 지점까지의 재작성·삭제를 탐지한다. 마지막
외부 체크포인트 이후 기록을 공격자가 재작성하거나, DB와 체크포인트를 함께 바꾸면
보장하지 않는다. 운영자는 내보내기 주기와 독립 저장 위치·접근 권한을 정해야 한다.
현재 자동 외부 전송·전자서명·보존 정책은 없다.

## 시스템 설정의 수동 검사

관리자는 시스템 설정의 ‘감사 로그 연결 검증’에서 전체 로컬 연결을 검사한다.
독립 보관한 체크포인트 JSON을 붙여 넣으면 그 지점의 연결도 함께 비교한다.
화면에 나온 체크포인트를 다시 입력하는 것만으로 독립 보관을 증명하지는 않는다.
결과는 검사 시점의 스냅샷이며 자동 갱신·상시 정상 상태 표시가 아니다.
로컬 연결 일치, 입력 체크포인트를 포함한 일치, 불일치, 검증 미완료를 구분한다.
입력 변경이나 재검사 시 이전 결과를 지우고, 오류 후 입력은 유지한다.

`POST /api/audit/verify`는 관리자 전용이며 본문은 `{}` 또는
`{"checkpoint":{"format":"aegis-audit-v1","chain_id":"…","seq":1,"hash":"…"}}`다.
추가 필드·잘못된 해시·정수가 아닌 seq는 422로 거절한다. seq는 서버에서 SQLite
정수 범위까지 허용하지만 화면은 JavaScript의 안전한 정수 범위를 넘어가면 CLI
비교를 안내한다. 이벤트 메시지·detail·사용자 정보는 결과에 포함하지 않는다.
검사 작업은 DB를 읽기 전용으로 열고 한 스냅샷을 순회한다. 검사 경로는 공통 POST
감사 기록에서 제외해 로그가 손상돼도 추가 기록 없이 결과를 반환한다. 자동 수리·
재봉인을 수행하지 않는다. 결과는 Cache-Control: no-store로 반환한다.

한 서버에서 동시 검사 1개를 허용하고 초과 요청은 429와 Retry-After: 5다.
10초의 협력적 시간 제한을 행 사이와 SQLite progress handler에서 검사한다.
시간 초과나 DB 읽기 오류는 검증 미완료다. 단일 큰 이벤트의 해시/JSON 인코딩을
강제 선점하지는 않으며 SQLite 잠금 대기는 최대 0.25초다. 화면을 떠나면 클라이언트
요청을 중단하지만 서버 검증은 자체 시간 제한까지 이어질 수 있다. 외부 체크포인트
보관·서명·장시간 부하는 별도 운영 절차와 검증이 필요하다.

불일치가 나오면 원본과 독립 체크포인트를 보존하고 마지막으로 신뢰하는 백업을
별도 경로에서 검증한다. 로그 삭제/재봉인을 수리 절차로 사용하지 않는다. 스키마 2
백업·복구는 이 연결을 검사하며, 외부 체크포인트와의 비교는 별도 명령으로 수행한다.
읽기 검증은 서비스를 실행 중에도 가능하지만 긴 읽기 스냅샷은 WAL 체크포인트에
영향을 줄 수 있다. PostgreSQL 지원·대규모 부하·자동화된 외부 보관은 후속 작업이다.


감사 CLI는 기본 HTTP 저장소 선택 환경을 따른다. PostgreSQL은
`AEGIS_STORAGE_BACKEND=postgres`와 DSN/schema가 필요하며
`aegis-verify-audit --backend postgres --schema aegis_workspace`로도 선택할 수 있다.
이 모드의 `--source`는 거절한다. 기존 체크포인트 입력·새0600 파일 출력·덮어쓰기
거절·실패 종료 코드2는 유지한다. [네이티브 읽기 계약](POSTGRES-STORAGE.md)을 따른다.
