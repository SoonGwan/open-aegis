# 내장 검증 도구의 실행 계약

계획 생성 시 `tool_contracts`에 선택한 내장 도구의 계약을 저장한다. 일반 작업,
재검증, 재실행, 예약에서 만드는 계획에 동일하게 적용한다. 클라이언트가 보낸
계약으로 덮어쓰지 않는다. 현재는 검토된 6개 내장 도구만 제공하며 외부 Python·셸
도구 등록이나 일반 플러그인 로딩은 제공하지 않는다.
별도 [MCP 관리자 메타데이터 등록](REMOTE-MCP.md)은 실행 가능 도구의 이 계약과
구분하며, 등록만으로 내장 도구·Worker·작업 커버리지에 포함되지 않는다.
별도 [서명된 MCP 실행 서버](MCP-EXECUTION.md)는 이 내장 결과 계약을 재사용한다.
운영자가 구성하고 관리자가 정의를 검토한 고정 어댑터는 메인 앱의 승인/Worker와
연결한다. 등록만으로는 실행하지 않으며 일반 외부 도구에는 이 권한을 부여하지 않는다.

## 승인과 실행

계약은 `aegis-tools-v1` 형식, 패키지 코드 지문, 선택 순서대로 저장한 도구 목록이다.
각 항목은 도구 ID·계약 버전(현재 1)·GET 방식·권한 설명·결과 형식과 결과 상한을
포함한다. 기본 응답 관찰은 모든 도구에, 추가 범위 내 GET은 API 권한 검증에,
링크 관찰은 엔드포인트 관찰에만 선언한다. 실제 주소·요청·시간 제한은 승인 범위와
[실행 정책](RUNTIME.md), 기존 Transport가 검사한다.

승인은 현재 계약과 전체 내용을 비교한다. 버전·지문·상한·권한·선택 순서가
다르거나 계약이 없으면 409로 거절한다. 추가 필드나 버전 `true`·`1.0`도 정수 `1`과
같은 계약으로 취급하지 않는다. 승인 후 대기열에서 실행을 시작할 때 Planner보다
먼저 다시 검사하고, Worker의 기본 대상 요청 전에도 검사한다. 실행 전 불일치는
해당 작업·커버리지를 실패 처리하고 `termination_reason=tool_contract_changed`로
기록한다. 승인 이벤트에도 당시 계약을 남긴다.

승인 목록과 작업 상세는 계약 버전·결과 상한·코드 지문을 보여주고 불일치 계획의
승인 버튼을 비활성화한다. 화면 검사는 안내이며 서버 검사를 대신하지 않는다.
이전 완료 기록에는 현재 도구와 다를 수 있다는 설명을 표시한다. 과거 기록을
현재 계약으로 소급 변경하지 않는다.

## 업데이트와 이전 계획

코드 지문은 프로세스에서 이 모듈을 불러올 때 `aegis` 패키지 안의 `.py` 파일을
경로 순서로 SHA-256 해시한 값이다. 관련 없는 Python 코드 변경도 이전 계획을
무효화할 수 있는 보수적인 기준이다. 프런트엔드·문서 수정만으로는 바뀌지 않는다.
도구의 의미나 입출력 계약이 바뀌면 계약 버전도 갱신한다.

이 기능 도입 전 승인 대기 계획에는 계약이 없다. 승인 목록·작업 상세의
‘현재 범위로 새 계획’은 현재 자산 revision·실행 정책·도구 계약을 읽어 별도의
승인 대기 계획을 만든다. 원본의 자산 선택·검증 도구·목표를 유지하며 원본 범위는
수정하지 않는다. 새 계획은 반드시 다시 승인해야 한다.

관리자·운영자는 `POST /api/tasks/{id}/replan`으로 같은 동작을 수행할 수 있다.
원본은 `rejected`·`termination_reason=replanned`로 남고 `replaced_by`로 새 계획을,
새 계획은 `replan_of`로 원본을 가리킨다. 원본의 미실행 커버리지는 취소되며
원본·새 계획·두 커버리지 변경은 같은 SQLite 트랜잭션으로 저장된다. 감사 이벤트는
이 비즈니스 트랜잭션 이후 별도로 저장된다. 동시 승인과 재계획은 하나만 성공하며
같은 원본에 대한 재시도는 이미 만든 새 계획을 반환한다. 보관된 자산은 먼저 복원해야
하며 생성 오류 시 화면은 원본을 유지하고 재시도를 제공한다. 예약·재검증 연결과
현재 발견의 조치 버전은 새 계획에 보존된다. 같은 프로세스의 단일 워크스페이스
잠금 기준이며 여러 서버 인스턴스의 동시 변경을 보장하지 않는다.

 실패·중지·재시작 중단
작업의 재실행은 원본을 보존하면서 현재 계약으로 새 승인 계획을 만든다. 기존 계획을
자동으로 다시 승인하거나 계약을 자동 보충하지 않는다. 도구 갱신 후에는 서버를
정상 종료·재시작한다. 진행 중 작업의 재시작 처리는 기존 중단 정책을 따른다.

이 지문은 호환성 비교이며 전자서명·게시자 인증·변조 방지 증명이 아니다. 실제
로드된 명령의 지속적인 측정, Python 메모리 변경, 의존성·인터프리터·운영체제 변경을
탐지하지 않는다. 프로세스와 코드 파일을 관리하는 운영자는 신뢰 경계 안에 있다.
정책 재현 CLI는 현재 검증기로 명시적인 `--run`을 수행하는 별도 흐름이며 원래
검증기 버전 그대로 실행하는 재현이나 이 작업 계약의 인증을 보장하지 않는다.

## 결과 저장 전 검사

한 도구가 반환한 결과 전체를 검사한 후 발견·관찰을 저장한다. 제한은 다음과 같다.

- 발견 최대 128개, 엔드포인트 관찰 링크 최대 100개. 다른 도구는 링크를 반환할 수 없다.
- 전체 결과 JSON 최대 512 KiB, 구조 깊이 16, 노드 4,096개, 개별 배열·객체 256개 항목.
- 발견의 정확한 필드·해당 도구 ID·심각도·판정 유형, 코드 128자·제목 300자·수정 안내 4,000자.
- JSON 값과 유한 숫자만 허용한다. 알 수 없는 필드, 비 JSON 값, 지나친 구조는 거절한다.
- 링크는 최대 2,048자이며 정규화된 승인 범위 내 주소여야 한다. 쿼리·fragment는 저장하지 않는다.
- 건너뜀 사유는 최대 1,000자다. 건너뜀과 부분 발견·링크를 함께 반환할 수 없다.

두 번째 발견이 잘못됐으면 첫 번째도 저장하지 않는다. 해당 도구는 판정 불가/실패로
남고 재검증이 해결로 판정되지 않는다. 다른 정상 도구 결과는 기존 정책대로 유지한다.
입력·응답 내용이나 검증 오류 원문은 오류 이벤트에 복사하지 않는다.

이 검사는 생성된 결과의 저장 입장 제한이다. 검증 함수가 결과를 만드는 동안의
CPU·메모리 사용을 강제로 격리하지 않는다. 결과 직렬화 전에 구조와 문자열 예산을
검사하지만 프로세스 RSS 상한을 보장하지 않는다. 일반 JSON 증거 구조를 허용하므로
새 도구의 비밀정보 비저장은 별도 코드 검토·실행 검증이 필요하다. 권한 설명만으로
임의 코드의 부작용을 제한할 수 없다. 외부 도구 등록·실행 격리·결과 계약의 확장은
[v1 출시 기준](V1-READINESS.md)의 미완료 항목이다.
